## Running it

Two processes. Backend first.

```bash
# Backend — from repo root (venv is at ./.venv, Python 3.14.6)
.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000   # run from ./backend

# Frontend — from ./frontend
npm run dev        # Vite dev server, default port 5173
npm run build      # production build into frontend/dist (gitignored)
npm run lint       # ESLint 10
```

Docs are auto-served at `http://127.0.0.1:8000/docs` (Swagger), `/redoc`, `/openapi.json`.

**Always clean up processes you start.** Leaked servers have broken this environment twice — a stray listener on 8000 causes `[Errno 10048] only one usage of each socket address`, and a stray Vite server causes confusing CORS/preflight failures against a backend that looks fine. In Git Bash:

```bash
netstat -ano | grep -E ':8000|:5173'
taskkill //F //T //PID <pid>          # note the doubled slashes under Git Bash
```

Note `uvicorn --host 127.0.0.1` binds IPv4 only; `vite dev` and `vite preview` may bind `[::1]` only. If a URL refuses while the server is clearly up, that mismatch is usually why — try `localhost` vs `127.0.0.1`, or pass `--host 127.0.0.1`.

There is also a zero-dependency browser driver that loads every route and checks the rendered text — see "Verifying in a real browser" below. Lint and build cannot catch a leaked i18n key or a `null%`, so run it after any UI change.

### Frontend routes

`/` landing → optional `/login` (name, phone, address, email — no password, nothing authenticated, it carries the name into step 1) → 4-step journey `/profile` → `/business` → `/location` → `/finance` → then 4 result pages `/analysis`, `/schemes`, `/advisory`, `/report`, plus a `*` catch-all rendering `NotFoundPage`. ### Client state — sessionStorage, versioned

`AppContext` ([AppContext.jsx](frontend/src/context/AppContext.jsx)) holds every answer and the API result, and mirrors the whole thing into **`sessionStorage['sih-application']`** as `{v: STORAGE_VERSION, data}` on every change. `profile` holds `name`/`language`/`dialect`/`literacyLevel`; **state and district live only on `location`** — they used to be duplicated on `profile` and asked for twice. `location.marketType` is an **array** (multi-select), not a string.

Four things about this are load-bearing:

- **`sessionStorage`, not `localStorage`, and that is deliberate.** Someone's revenue, debt and EMI must not sit on a shared demo laptop after they walk away, and a closed tab being a clean slate is what we want between two judges. Within one tab it survives a refresh, which was the whole point — a refresh used to wipe the demo and drop every result page to its empty state.
- **`STORAGE_VERSION` must be bumped whenever the `EMPTY` shape changes.** A payload with a mismatched `v` is discarded rather than half-restored.
- **`hydrate()` merges section-by-section over `EMPTY`, never trusting the stored object wholesale.** A field added after a payload was written would otherwise arrive `undefined`, and React silently converts a controlled input with an `undefined` value into an uncontrolled one — the field stops updating and nothing in the console says why.
- **`resetApplication()` is the only way back to a blank form** without closing the tab. `StartOverButton` in the utility bar calls it, and renders only once there is something to lose — which is **`isStarted(data)`, exported from `AppContext` and derived from `EMPTY`, not a hand-listed set of fields.** It used to test 6 of the 21 answer fields `EMPTY` declares (profile 4, business 8, location 6, finance 3 — 19 of them are questions a reader is actually asked, since `categoryOther` only appears for "Other" and language/dialect are also settable from the utility bar), so someone who had typed their expected monthly revenue and nothing else — a perfectly ordinary way to start — had their figures sitting in `sessionStorage` with **no control anywhere in the app to clear them** short of closing the tab, which is the whole reason the storage is per-session on a shared laptop. It has to be a *difference from `EMPTY`* rather than a truthiness test, because half the defaults are not blank: `locationType` is `'rural'`, `language` `'Hindi'`, `literacyLevel` `'low'`, `employees` `0`. And `marketType` needs its own arm, since `[] !== []` for every pair of arrays.
- **Editing an answer clears the result. `updateSection` sets `result: null` for `business`, `location` and `finance`.** A stale result is worse than no result: nothing guards the journey order, so someone who has seen `/analysis` can go back to `/business`, change Tailoring to Retail, then click Schemes and read the tailoring schemes as though they had matched retail — and **every figure and card is internally consistent, which is exactly why nothing on the page gives it away.** Three details are load-bearing. `profile` is deliberately *not* in `ANSWER_SECTIONS`: name, language, dialect and literacy level are echoed back rather than computed from, so changing one cannot make a number wrong, and clearing on them would mean switching language on `/profile` silently threw the results away — the one thing this demo does on purpose. `updateSection` returns the *same object* when nothing actually changed, which is not an optimisation but the guard that stops an idempotent call from discarding a still-valid result. And on `/finance` the field handlers clear while the submit's `setResult` runs after, so the submit path is unaffected. **Demo consequence:** going back to change an answer sends the result pages to their empty state, by design — re-submit `/finance` to get them back.

Language and dialect are separate, in `localStorage` (`sih-language`, `sih-dialect`) — a UI preference is not personal financial data, and it *should* outlive the tab. Theme (`sih-theme`) and text size (`sih-textsize`) are there for the same reason. `sih-contrast` was a third key until 8 Sept 2026; nothing reads it now, so a returning visitor's copy of it is inert rather than a bug.

Result pages still cannot be *deep-linked* from a cold tab — there is no URL state — but a refresh no longer loses anything.

### Language, dialect and location data

**8 languages**, each with its endonym and a sample line so a reader who cannot read English can still find their own script: `en`, `hi`, `ta`, `te`, `ml`, `kn`, `mr`, `bn` ([languages.js](frontend/src/i18n/languages.js)). **`DEFAULT_LANGUAGE` is `hi`** — the target user is a rural micro-entrepreneur, so Hindi is the default and English is the fallback, not the reverse.

Strings live in **four** files, split purely by size and by who wrote the sentence. Each exports one dict per language code, and `merge()` in `strings.js` spreads them in this order — so a key defined in two files means the later file silently wins and the earlier text is dead code:

| File | Keys × 8 | Holds |
|---|---|---|
| [strings.js](frontend/src/i18n/strings.js) | 190 | chrome, landing, the four data-entry steps — and the `merge()` that assembles the other three |
| [resultStrings.js](frontend/src/i18n/resultStrings.js) | 213 | the four result pages, `/login`, `/404`, and the enum→label maps' targets (`st.*`, `risk.*`, `lvl.*`, `lvlnote.*`) |
| [backendStrings.js](frontend/src/i18n/backendStrings.js) | 38 | sentences a **Python service composes** (`adv.*`, `obs.*`, `rsn.*`, `sum.*`, `nxt.*`, `why.*`, `seas.*`, `src.*`) |
| [schemeStrings.js](frontend/src/i18n/schemeStrings.js) | 188 | prose **typed into schemes.json** (`sdata.*`, `elig.*`, `doc.*`, `scat.*`) |

**629 distinct keys, 5,032 strings** — measured by `parity4.mjs`, which prints the total. (618 until 23 Sept 2026, when the total rose by a net eleven: the nine funding-gap strings, see "The funding gap counted", and two from the scheme-fit fix the same day, which added five and deleted three. The net two are `sc.fitRegion` in `resultStrings.js` and `why.regionSpecific` in `backendStrings.js` — see "Scheme fit shown as what it is".) The split rule is one line: *if a Python function builds the sentence it belongs in `backendStrings.js`; if the sentence is typed into `schemes.json` it belongs in `schemeStrings.js`.*

It was 584 until 8 Sept 2026. `common.appName` and `landing.eyebrow` were **deleted**, not retranslated — see "The product name is not a translatable string" below. `common.highContrast` went the same way when high contrast was removed later that day; `man.tipText` was **rewritten** in all 8 languages rather than deleted, because its third tip named that control and the string itself is live manual copy.

**All 8 dicts are at full parity in all four files — verified by script, not by self-report.** `node tools/parity4.mjs` from the repo root checks five things nothing else can see, in order of how badly each bites: every language carries every `en` key per file; no duplicate key inside one dict; **no key defined in two different files**; no non-English value byte-identical to English (the per-key fallback never fires, so the reader just sees English and nothing reports it); and placeholder sets matching English. It is zero-dependency and exits 1 on failure. Run it after touching any dictionary.

Two figures in this file used to read "344 keys" and "186 keys". They were stale by a wide margin in both directions; the table above is measured.

**A third figure in that same table was wrong until 10 Sept 2026, and the way it was caught is the point.** `resultStrings.js` read **211**, so the four per-file counts summed to **619** against a documented total of **618** — and the two numbers sat nine lines apart in this file for a day. The sum is not decoration: **parity4's third check forbids any key from being defined in two files, so the per-file counts MUST add to the total exactly.** A discrepancy of one is therefore not a rounding difference, it is proof that one of the five numbers is wrong. It was `sc.openSite` — deleted with the outbound links, which took `resultStrings.js` to 210 while this row kept the pre-deletion figure.

Two things follow, and the second is the expensive one. **Do not trust "the table above is measured"** — that sentence was written when it was true and does not re-verify itself; `node tools/parity4.mjs` prints all five numbers in one line and takes under a second. And **an inconsistent fact is worse than a missing one, because a reader will reconcile it rather than doubt it**: briefed with 211 against 618, three separate writers independently invented the same explanation — "one key must be defined in two files" — which is the exact thing parity4 exists to forbid. A doc that contradicts itself by one does not read as broken; it reads as a puzzle with a clever answer.

**The product name is not a translatable string.** It is `APP_NAME` in [i18n/brand.js](frontend/src/i18n/brand.js), one exported constant, and its value is **`अर्थNiti`** — Devanagari अर्थ ("wealth") plus Latin *Niti* ("policy"). The mixed script is the logo's own wordmark; do not transliterate either half, and do not "fix" it to `ArthNiti`, which is the old spelling and appears nowhere in the app.

It used to be `common.appName` plus `landing.eyebrow`, translated eight ways (अर्थनीति / அர்த்நீதி / అర్థనీతి / …). That is wrong for the same reason a bank does not rename itself per language: **switching the interface to Tamil renamed the product**, so a judge toggling languages mid-demo saw four different names for one app. Both keys were deleted and every touchpoint — the masthead, the breadcrumb, the footer, the landing eyebrow, the `/report` sheet header, `<title>` and the meta description — now reads from the constant, so the name cannot drift between them either.

Two mechanical consequences:

- **Deleting was the only option; homogenising the eight dicts would not have worked.** parity4's fourth check rejects any non-English value byte-identical to English, with an `ALLOW_IDENTICAL` escape for values that are pure punctuation, digits and Latin. `ArthNiti` would have slipped through it; **`अर्थNiti` would not**, because it contains Devanagari. Putting the same brand string in all eight dicts fails the parity script by design.
- **A sentence that names the product carries it as an `{app}` placeholder.** `login.title` is the only such string left (`'Log in to {app}'`, `'{app} में लॉग इन करें'`, …), so the sentence around the name is still translated while the name is not. Note how the case languages handle it: Tamil/Telugu/Malayalam/Kannada/Bengali attach the locative or dative suffix to the placeholder with a hyphen (`{app}-யில்`, `{app}-லో`, `{app}-ൽ`, `{app}-ಗೆ`, `{app}-তে`) because that is the convention for a foreign-script word; Hindi and Marathi use a free postposition (`{app} में`, `{app} मध्ये`). Any new sentence naming the product must follow this and must never be built by concatenation in JSX — see the composition rule above.

`common.appTagline` is still translated in all 8 languages, and correctly so: a tagline is a sentence, not a name.

**The English fallback is per key, not per language.** `lookup()` tries the dialect override, then the chosen language, then `en`, then returns the key itself ([LanguageContext.jsx:16-28](frontend/src/i18n/LanguageContext.jsx#L16-L28)). Two consequences worth knowing:

- You can add an English key and use it immediately; the other 7 languages show English for that one string and stay correct everywhere else.
- A **typo'd or missing key renders as the literal dotted name** (`money.left`) on the page. Lint and build cannot catch this — nothing imports the key names. `tools/verify/drive.mjs` greps rendered text for the known key prefixes precisely because this is the one failure class only a browser can see.

`t(key, values)` fills `{name}` placeholders by plain string replacement. **No plural rules and no number formatting** — Indic plurals and grammatical case are real problems, so the strings are written to avoid needing them. Corollary: **never compose a sentence from parts in JSX.** `t('label') + ' ' + value + '.'` puts English word order and a Latin full stop into a Devanagari sentence (which ends in `।`). Give the whole phrase its own key with a placeholder. This is also why `mk.demandHigh` / `mk.demandMedium` / `mk.demandLow` are three keys rather than one `'{level} demand'` template — that template produced the literal "Medium मांग".

**Dialects cascade from the language** and are a *curated phrase layer*, not a translation: `DIALECT_PHRASES` overrides a handful of the highest-visibility strings (the greeting, the CTA, the words for money) for 9 of the 30 listed varieties. Anything not overridden falls through to the language, so a dialect with no entries is still a fully usable UI. `setLanguage` **clears the dialect**, the same way changing state clears the district. Don't overclaim this in the demo — say "dialect-aware phrasing", not "translated into Bhojpuri".

**The greeting is the string that makes the feature visible, and until the 8 Sept audit it rendered nowhere.** `greeting.hello` was translated into all 8 languages and overridden by **all 9** dialect phrase sets, and no component used it — so it was 8 translations and 9 overrides of dead weight, and picking a dialect changed nothing a reader could see on the landing page. Count what was left: each of the 9 sets holds at most three keys, and for `ta-madurai`, `te-telangana`, `ml-malabar` and `bn-sylheti` the other two are `landing.cta` (which only the Hindi dialects override) and `money.left` (a result page) — so **choosing one of those four dialects had no visible effect until all four forms were filled in**. The landing eyebrow now renders `greeting.hello` in place of the product name, which is also why the name is not lost: the masthead sits directly above that line and, since 11 Sept 2026, carries the wordmark itself. So the demo advice under "Safest demo configuration" is now literally true rather than aspirational — pick a dialect on the landing page and the greeting changes on the spot.

The selection reaches the backend through the fields the contract already carried: `apiLanguage` → `user_language`, `apiDialect` → `preferred_dialect`. **The backend still does nothing with them** — it echoes them back in `mvp_summary`. All result-page *prose* is backend-generated English.

**What is and is not translated on a result page.** This section used to say backend prose was never wrapped in `t()` and always printed in English. **That gap is closed** — read the rest of this section before assuming otherwise, because the mechanism has a rule that is easy to break.

Our own labels go through `t()`. Backend prose goes through **`tBackend()`**, and the two have *opposite* fallback contracts:

- `t(key)` → dialect override, then language, then `en`, then **the key itself**. A typo renders as the literal dotted name on the page. That visibility is the point.
- `tBackend(code, english)` → the translation for `code`, else **the English sentence the backend already sent**. It must *never* print a dotted code — there is always real prose to fall back to, so a scheme added without codes still renders, just untranslated.

Every service that composes a sentence now emits a code beside it: `advisory.recommendation_codes`, `business_analysis.observation_codes`, `risk_analysis.reason_code`, `mvp_summary.message_code`/`next_step_code`, market `seasonality_code`/`source_code`, and per scheme `description_code`, `support_type_code`, `match_reason_codes[]`, `eligibility_codes[]`, `document_codes[]`. [backendText.js](frontend/src/i18n/backendText.js) is the single place that resolves them — `useBackendText()` returns `advice`, `observations`, `riskReason`, `summaryMessage`, `nextStep`, `seasonality`, `marketSource`, `schemeDescription`, `schemeSupport`, `schemeReasons`, `schemeEligibility`, `schemeDocuments`, `schemeLevel`, `schemeLevelNote`, `schemeFit`. It is shared rather than duplicated per page precisely because a copy that drifts shows a user English on one page and their own language on the next.

**The lockstep rule.** `eligibility_codes` / `eligibility_rules` and `document_codes` / `documents` are **index-aligned arrays**. Insert an English rule without inserting its code at the same index and every later rule silently gets the wrong translation — which reads perfectly fluently and is completely wrong. `test_every_scheme_carries_complete_translation_codes` asserts the two arrays are the same **length** — which catches a rule added with no code at all, and **cannot catch a code inserted at the wrong index**, because equal length says nothing about order. That second case is the one that reads fluently and is completely wrong, and nothing automated sees it. Do not weaken the length check, and do not read it as more than it is: an inserted rule needs its code inserted at the same index, verified by eye.

**Two things are still English by construction.** `match_reason_codes[]` carries a `categories` list rather than a finished sentence, because the reason names the *scheme's own* wording for a kind of work — the frontend translates each word through `CATEGORY_KEYS` in `backendText.js` and rejoins, so a sentence is never assembled from a translated template plus untranslated English fragments. And backend **enums** stay English internally because they are load-bearing: `financial_status`, `risk_level`, `feasibility_status`, `match_level`, the scheme `level` and the scheme `fit_basis`. They become plain language only at render, via the `STATUS_KEYS` / `RISK_KEYS` / `CHOICE_KEYS` maps each result page carries and the `LEVEL_KEYS` and `FIT_KEYS` maps in `backendText.js`. An unrecognised enum value still prints, title-cased, rather than vanishing. That is also why the tier keys are camelCase (`lvl.subDistrict`, not `lvl.sub_district`) — a mistyped key would otherwise leak an underscore into the page.

**Digits stay Latin** and money stays `'en-IN'`-grouped even in Tamil or Telugu — that is what is printed on Indian currency and on government forms.

**`data/indiaLocations.js` drives the cascading dropdown**: 36 states/UTs, 768 districts, `districtsForState(name)` returning `[]` for an unknown state so the caller can render a disabled empty select with no special-casing. The district select is `disabled` until a state is chosen, and **`handleStateChange` clears `district`** — otherwise "Lucknow" would survive a switch to Kerala and be sent to the backend, which would then look up a district that cannot exist there. District names are indicative and in the Latin script that appears on official documents; boundaries change, so re-check before any real deployment.

**Category and market-type values sent to the backend must stay English.** `CATEGORY_SYNONYMS` in `scheme_service.py` keys off the exact strings `retail`, `food processing`, `handicrafts`, `tailoring`, `agriculture`, `dairy`, `services`, `manufacturing`, `other`. Only the *label* is translated — the tuple in `BusinessPage.jsx` is `[value, icon, labelKey]` for exactly this reason. Same for `locationTypes` and `marketTypes` on `/location`.

## The data contract

Request — `UnifiedAnalysisRequest` ([schemas/analysis.py:4-34](backend/app/schemas/analysis.py#L4-L34)). Required: `business_category` (min 2 chars), `state` (min 2), and `available_capital`, `monthly_expenses`, `expected_monthly_revenue`, `monthly_emi`, `initial_investment`, `monthly_operating_expenses` (all `>= 0`). Optional with defaults: `employees` 0, `existing_debt` 0, `district`/`village`/`market_type`/`customers` `""`, `user_language` "Hindi", `preferred_dialect` `None`, `literacy_level` "low", `entrepreneur_type` `None`, `location_type` "rural". Validation failures return **422**.

`entrepreneur_type` is still accepted by the schema and still echoed in `mvp_summary`, but **no page collects it and the frontend no longer sends it** — it is always `None`. Don't wire a UI field to it without deciding what should consume it.

**A 422 body's `detail` is a list of objects, not a string.** `readErrorMessage` in [api.js](frontend/src/services/api.js) turns it into one plain-language sentence using a `FIELD_LABELS` map. Passing `detail` straight to `Error()` renders as the literal string `[object Object]` — that was a live bug.

**Each `FIELD_LABELS` phrase must echo the wording of the question that collects the field**, because the reader's next action is to walk back through the steps and find it. "the money you already have" is findable on `/finance`; "available capital" appears nowhere in the UI, so naming it tells the reader a field is wrong and gives them no way to locate it. Four labels were rewritten on that basis (`business_category` → "the kind of work you do", `expected_monthly_revenue` → "the money you expect to earn each month", `initial_investment` → "how much money you require", `monthly_operating_expenses` → "how much the business itself will cost each month"). The same rule binds the translated `errf.*` keys, and it is the plain-language rule applied to an error path — the place it is easiest to forget.

Response — **7** top-level keys ([analysis_service.py:106-114](backend/app/services/analysis_service.py#L106-L114)). These are the exact and complete key sets:

| Section | Keys |

| `risk_analysis` | `pressure_ratio_percent`, `risk_level`, `risk_level_without_new_loan`, `reason`, `reason_code`, `monthly_emi`, `estimated_new_emi`, `total_monthly_emi`, `assumed_interest_rate_percent`, `assumed_tenure_months` — everything after `reason_code`, plus `risk_level_without_new_loan`, added 23 Sept 2026 for the funding gap |

**This table was stale in six of its seven rows until 8 Sept 2026, and the reason it stayed stale is worth knowing before trusting any similar list.** It was written before the translation-code layer and never updated, so every `*_code` field — the entire mechanism the i18n section above describes at length — was undocumented, along with `scheme_matches`'s `level` and `scheme_id`. Nothing caught it, because the contract tests **subscript the documented keys**: removing or renaming one raises `KeyError`, but *adding* one passes silently. The same asymmetry is what let defect 4 survive. So the tests pin this table as a lower bound only, and the way to confirm it is to call the service and print `list(v.keys())` — which is how the rows above were produced.

Enumerated values: `scheme_matches[].fit_basis` ∈ `state` / `region` / `national`. `financial_status` ∈ `profitable` / `break_even` / `loss`. `risk_level` ∈ `low` / `moderate` / `high`. `feasibility_status` ∈ `feasible` / `break_even` / `not_feasible`. `mvp_summary.status` ∈ `good` / `attention_needed` / `review`. `market_context[].match_level` ∈ `district` / `state`.

`match_level` is not decoration — it is the honesty marker on the hyperlocal claim. `district` means the row is the entrepreneur's own district; `state` means we had no row for their district and fell back to the same state. Both `/analysis` and `/report` print a different sentence for each. Never render a `state` row as though it were local.

Two different expense notions flow through, and mixing them up is easy: `monthly_expenses` drives `financial_analysis.monthly_profit`, while `monthly_operating_expenses` drives `business_analysis.monthly_operating_surplus`. They are separate inputs and can disagree.

### The scheme dataset — 30 schemes across 7 tiers

`schemes.json` grew from 3 to **30** on 7 Sept 2026, on the brief "include Block/Taluka/Circle, Village/Urban Local Body, Regional, District, Sub-District, State/UT and Central schemes". Every scheme carries a `level`, and that is the axis the UI is organised around:

| `level` | rank | Examples in the file |
|---|---|---|
| `central` | 0 | PMEGP, PMMY, PMFME, PM Vishwakarma, Stand-Up India, NLM, AHIDF, AIF, KCC |
| `state` | 1 | UP Mukhyamantri Yuva, UP VSSY, Maharashtra CMEGP, Tamil Nadu NEEDS, Kerala ESS, Bengal Bhabishyat Credit Card, Karnataka Udyogini |
| `regional` | 2 | UNNATI (North East), Vibrant Villages (border blocks) |
| `district` | 3 | District Industries Centre, RSETI, Krishi Vigyan Kendra, ODOP (UP) |
| `sub_district` | 4 | Tehsil/Taluka certificate counter, Sub-Divisional agriculture office |
| `block` | 5 | BDO / NRLM SHG desk, Block Level Bankers' Committee, ATMA block unit |
| `local_body` | 6 | Gram Panchayat trade licence, Common Service Centre, PM SVANidhi (urban local body) |

**Every scheme also carries a `location_types` list**, added 8 Sept 2026 and mirroring `states` exactly: 25 are `["ALL"]`, four are `["rural"]` (Vibrant Villages, RSETI, the BDO/NRLM livelihoods desk, the Gram Panchayat trade licence) and PM SVANidhi is `["semi-urban", "urban"]`. Only a scheme whose *own* eligibility text names a settlement type is restricted here — the default is everywhere, and `Scheme.location_types` defaults to `["ALL"]` for the same reason `level` does, so a scheme dict written in a test before the field existed still loads rather than failing validation.

**Two field-name traps in this dataset, both measured.** The JSON field is **`business_categories`** — `Scheme.business_categories` in `schemas/scheme.py`, and that is the key `schemes.json` actually carries. But `_scheme_index()` re-keys it to the shorter **`categories`** ([scheme_service.py:306](backend/app/services/scheme_service.py#L306)), which is what `match_schemes` then reads (`entry["categories"]`). So **the same data has two names depending on which side of the index you are on**, and the Formulas note below about "`categories` stays an ordered tuple" is about the *index*, not the file. Subscripting `scheme["categories"]` on a raw dict loaded from the file raises `KeyError`; subscripting `scheme["business_categories"]` on an index entry does the same. Neither mistake is caught by a type hint.

And **`target_segment` exists on every scheme and nothing reads it.** It is declared on the `Scheme` model, emitted by `gen_schemes.py:630`, and present in all 30 records — but no service touches it, it is **not** among `scheme_matches`'s 16 keys, and no frontend file mentions it. So it is inert rather than broken: dataset content with no consumer, which is why it never appeared in the response table. It is the most obvious candidate if a card ever needs a "who this is for" line, since the text is already written and already translated nowhere — note that adding it to the response means adding a `target_segment_code` too, or it would be the one English string on an otherwise translated card.

`LEVEL_RANK` in `scheme_service.py` holds those ranks; `level_rank(level)` is tolerant of an unknown value; `DEFAULT_LEVEL` is `"central"`. Matches sort by **`(-match_score, level_rank, name)`** — score first, then outward from the national government, then alphabetically. Sorting on score alone left thirty schemes in *file* order within each score, so the same category could list a Gram Panchayat counter above PMEGP.

The frontend mirrors this: `LEVEL_ORDER` in [backendText.js](frontend/src/i18n/backendText.js) must stay in step with `LEVEL_RANK`. **`/schemes` groups the cards by tier** under a `lvl.*` heading with a `lvlnote.*` line beneath it; `/analysis` and `/report` are flat lists and carry a `sch.runBy` badge on each card instead. The `lvlnote.*` strings cost 64 extra translated keys and are worth it: a tier label alone teaches a rural reader nothing, so the note names the office they would physically walk into ("The block office near you. Its staff come to villages."). Empty tiers are dropped, so a category matching only central schemes shows one heading rather than seven.

[gen_schemes.py](backend/gen_schemes.py) is the generator that produced the file, kept as **provenance rather than runtime** — nothing imports it and the backend reads only `schemes.json`. It is how to regenerate the dataset consistently if the tiers change; `gen_schemes_keys.json` records the key inventory it emitted (`{eligibility: 94, documents: 21, ids: 30}`).

**The dataset carries no `official_url`, and that is deliberate as of 10 Sept 2026.** Every scheme used to hold a link to its own government portal, 29 of the 30 confirmed HTTP 200 on 7 Sept; the owner's instruction was to remove them because deep-linking a reader into a government service from an unaffiliated student prototype is not ours to do. See "The outbound government links removed" below for what went and why the field is not coming back. `last_verified` stays — it is provenance about when the *rules* were transcribed, not a link.

### Formulas and thresholds

All deterministic, all unit-tested. Keep them that way — never move arithmetic into a model.

- `monthly_profit = expected_monthly_revenue - monthly_expenses`; margin = profit/revenue×100, and **`None` when revenue is 0** — this line used to say "0 when revenue is 0", which was the bug. A margin needs revenue to be a share *of*, and that branch is reached exactly when someone has entered expenses but no expected income, which is a loss; printing `0%` there reads as break-even. It now matches `estimated_roi_percent`, which already returned `None` for the same reason ([financial_service.py](backend/app/services/financial_service.py))
- `funding_gap = max(initial_investment - available_capital, 0)` — clamped, so surplus capital reads as no gap rather than a negative one. `/report` prefers this over its own client-side sum so the two pages cannot disagree.
- `pressure_ratio = total_monthly_emi / monthly_surplus × 100`, where **`total_monthly_emi = monthly_emi + estimated_new_emi`** and `estimated_new_emi` is the `funding_gap` priced as a new loan at **12% a year over 60 months** (standard annuity, rounded to the rupee; `0` when there is no gap). **<30 low, 30–50 moderate, >50 high**, taken on the total. Non-positive surplus short-circuits to `high` with `pressure_ratio_percent: None` ([risk_service.py](backend/app/services/risk_service.py)). `risk_level_without_new_loan` is the same band on the entered EMI alone, so the advice can tell "your current loan is too heavy" from "a loan for the gap would be too heavy". **`existing_debt` is deliberately not counted**: it is the outstanding principal of the loan whose repayment is `monthly_emi`, so adding it would count one loan twice. The 12% / 60-month terms are an assumption, not a quote, and every page that prints the figure says so (`ch.pressureIncludesNew`).
- `estimated_roi_percent = (monthly_operating_surplus × 12) / initial_investment × 100`, or `None` when investment is 0 ([business_service.py:30-35](backend/app/services/business_service.py#L30-L35))
- Observation/advice text is chosen by margin bands at 10% and 30% ([business_service.py:63-71](backend/app/services/business_service.py#L63-L71), [advisory_service.py:23-31](backend/app/services/advisory_service.py#L23-L31))
- Scheme score: **+60** if the category matches, then geography splits — **+40** if the scheme names the entrepreneur's own state (→ 100) or **+30** if it is open nationwide (→ 90). No category match returns `0, []` and the scheme is dropped ([scheme_service.py](backend/app/services/scheme_service.py)). The split exists because with 30 schemes a flat +40 for both put almost every match on exactly 100. **Only 90 and 100 are reachable, and the score checks no eligibility rule**, so it is **never printed as a percentage** (as of 23 Sept 2026). The same branch sets `fit_basis` — beside the +40 it is `state` when the scheme's `states` list names the reader's state and no other, and `region` when it names theirs among several (UNNATI's eight North-Eastern states, Vibrant Villages' six border ones); beside the +30 it is `national` — and that is what every card, badge and the chart print, as `sc.fitState` "Made for your state" / `sc.fitRegion` "For a few states, including yours" / `sc.fitNational` "For all of India". `match_score` stays in the response for the sort and for API callers; `state` and `region` both score 100, so that split changes the words and never the order. The chart on `/analysis` and `/schemes` renders only when at least two bases are present. See "Scheme fit shown as what it is".
- **Availability is decided before scoring, not by it, on two axes.** `serves_state(scheme, state)` drops a scheme whose `states` list names a specific set the entrepreneur is not in, and `serves_location(scheme, location_type)` does the same for its `location_types` list. Showing a Uttar Pradesh-only subsidy to a Kerala entrepreneur as a partial match is worse than not showing it: they would spend a trip to the block office on it. Both are gates rather than score modifiers so the scorer stays a pure explainer of fit. **An empty value on either axis means "do not filter", not "nowhere"** — a caller that does not know the entrepreneur's state or the kind of place they work must still see everything open to both, so `match_schemes`'s `location_type` defaults to `""`. Was state-only until 8 Sept 2026; see the audit section for what that cost.
- Category matching runs the user's pick through `CATEGORY_SYNONYMS` first, then keeps the substring test. The map only bridges wording (`retail`/`shop`/`kirana` → `trading`, `handicraft`/`tailoring` → `manufacturing`, `livestock` → `dairy`, **`dairy` → `poultry`**); **it must never widen real eligibility.** That last entry is the one that reads like a widening and is not, so the reason is worth keeping: the Livestock/Dairy button's *label* says livestock but it **sends the single word `dairy`**, and every scheme in the file that says "poultry" also says "dairy" — except the National Livestock Mission, which says "poultry" and "agriculture". So the one scheme the Livestock button was missing was the livestock mission itself, and this entry adds nothing else anywhere in the dataset. NLM's own printed rules name poultry, sheep and goat, piggery and fodder, so a dairy-cattle keeper who sees the card reads what it covers. Note the shape: **it is the reverse direction of `livestock` → `dairy` and had to be written separately**, because `expand_category` walks the map once and does not chase a synonym's own synonyms. Plain `agriculture` still maps to nothing on purpose — PMEGP and PMMY cover allied activities, not crop farming, and the schemes agriculture reaches are ones that name it directly. **12 in the file claim it, but no single request sees all 12 except a rural one in a state Vibrant Villages names**: Vibrant Villages lists six border states/UTs and is rural-only, and RSETI and the BDO/NRLM desk are rural-only too, so a rural reader anywhere else gets **11** and a semi-urban or urban reader **9** (measured 23 Sept 2026).
- **The matcher's direction is `if scheme_category in phrase`** — the *scheme's* word must be a substring of the *user's* phrase, not the reverse. Two consequences that have each been a live bug: a scheme must never claim the category `"livestock"` (the synonym map goes livestock→dairy, not dairy→livestock, so nothing would ever reach it), and never `"other"` (the Other button sends the user's typed text, not the literal word). `test_no_scheme_claims_a_category_the_matcher_cannot_reach` pins both.
- Market context is tiered: exact state+district+category first, else same state+category with `match_level: "state"`, else `[]` ([market_service.py](backend/app/services/market_service.py)). Before 7 Sept it required an exact district, so every district without a row got an empty section.
- **All 9 rows in `market_data.json` are in Uttar Pradesh** — Lucknow ×5 (dairy, poultry, food processing, handicrafts, tailoring) and Varanasi ×4 (handicrafts, food processing, dairy, tailoring). Measured, not read off the file's shape. **So the `state` fallback tier can only ever fire for a UP district that has no row of its own; every other state in the dropdown returns `[]` and shows the empty state.** That is a much narrower dataset than "tiered lookup with a state fallback" implies, and the tiering code is fine — there is simply nothing to fall back *to* outside UP. Two consequences worth holding: the demo must stay in UP for the market section to appear at all (which is why "Safest demo configuration" names Lucknow), and if a judge picks their own state expect that section to be empty and say why — it is 9 illustrative rows, labelled `src.prototypeEstimate` on the page, not a survey. Don't "fix" this by widening the fallback to ignore state: an indicative price from Lucknow is not evidence about Kerala, and printing it as though it were would break the `match_level` honesty marker that the whole hyperlocal claim rests on.

### Verifying in a real browser

Lint, build and pytest cannot see a leaked `t()` key, a `null%`, or a page that renders as an empty shell. [tools/verify/drive.mjs](tools/verify/drive.mjs) drives Edge over CDP with **zero dependencies** (Node 24 has a global `WebSocket`), seeds `sessionStorage` so result pages can be loaded directly, walks **7 passes → 36 page loads**, and writes text dumps, full-page PNGs and a `report.json`. It fails on: an unrendered page, a page exception, a leaked dotted i18n key, the bad tokens `null%` / `NaN` / `undefined` / `[object Object]` / `₹null`, and raw enum names (`fit_basis` among them). **It also runs a scheme-card check**, added 23 Sept 2026: on `/analysis`, `/schemes` and `/report`, for every scheme in the seeded result, it opens every `<details>` on the page, finds the card by its heading, and fails on `SCORE AS PERCENT` (a score-shaped `90%` / `100%` anywhere in the card), `FIT LABEL MISSING` / `WRONG FIT LABEL` (the card must print the `sc.fit*` string for its own `fit_basis` in the page's language, and no other) and `SCHEME CARD NOT FOUND`. The expected labels are imported from `resultStrings.js` with the same per-key English fallback as `t()`. **It exits 1 on any finding** — until 23 Sept 2026 it exited 0 either way and only `report.json` said otherwise.

**Each of these fifteen browser scripts owns a different failure class, and they use fifteen different CDP ports** — counted from the list, which is now the authority; the sentence said "thirteen" while naming twelve until `motion-audit` landed on 9 Sept 2026 (`drive` 9222, `mobile-audit` 9333, `hero-art` 9337, `brand-mark` 9339, `lang-layout` 9343, `manual-audit` 9341, `error-banner` 9347, `field-align` 9351, `hero-geom` 9355, `print-audit` 9359, `hero-vibrance` 9361, `load-perf` 9363, `motion-audit` 9365, `scroll-audit` 9367, `text-align` 9371) with separate profile dirs, so two can run at once. `hero-vibrance.mjs` sat on 9359 as well until 8 Sept 2026, which quietly broke that guarantee for the one pair most likely to be run together. Two more scripts drive a browser without being gates — `assetgen` on 9377 and `svgcheck` on 9378 — so **seventeen scripts in the repo open a browser on a port of their own**, and a grep for `DEBUG_PORT` finds only fifteen of them. **The two it misses are `svgcheck` (9378) and `load-perf` (9363), which name the constant `PORT`** — measured per file, because this sentence previously named `assetgen` as one of the two and `assetgen` in fact uses `DEBUG_PORT`. The practical consequence of getting it wrong is the opposite of harmless: someone grepping `DEBUG_PORT` before picking a port sees 9377 and misses **9363**, which is the one a gate already owns. **9369 is deliberately left free**: it was a throwaway probe's port during the scroll work, and the next one-off should reuse it rather than take a number a gate might want.

**`load-perf.mjs` is the only one that points at `npm run preview` rather than `npm run dev`, and that is not a detail.** `vite dev` serves unbundled modules and unminified source, so every figure measured against it describes a pipeline that never ships — hundreds of module requests where production has seven. It is also the only script that measures *time* rather than correctness, which forces two things the other thirteen do not need: **medians of 5 cold loads** (one sample read FCP as 456 / 272 / 480 ms going 1× → 4× → 8× CPU throttle, i.e. faster on a slower CPU, which is impossible and is the giveaway that noise exceeded the effect), and `about:blank` between navigations so each load's Performance entries are its own. It separates **transfer** from **execute** because they have opposite fixes — fewer bytes helps the first and does nothing for the second — and it asserts the app actually mounted (`.ui-shell` present, ≥200 chars rendered), because a fast blank page measures beautifully.

Its own first version had the same failure class this file keeps recording: **the resource probe filtered on `initiatorType === 'script' | 'link' | 'css'` and silently dropped 6 of 9 chunks**, because a chunk pulled by `<link rel="modulepreload">` does not report the initiatorType you would guess. Both builds then reported 3 assets while one of the baseline's 3 was the entire pre-split bundle — a comparison that looked like a **3× improvement** and was pure artefact. It now sums every resource entry and breaks them down after.

**`hero-vibrance.mjs` is a tuning instrument, not a gate**, and it is the only script here that is. `hero-art.mjs` asks "is the shipped backdrop visible and still AA-clear"; this one asks "which filter setting would be *more vibrant* without breaking either", which needs a metric `hero-art.mjs` does not have. Mean ΔL\* is a **lightness** distance, so two settings can score identically and look nothing alike — halving saturation moves colour without moving lightness at all. The metric it adds is chroma, C\* in CIE LCh (`sqrt(a*² + b*²)`) after the composite. It sweeps candidates through the real composite in a canvas rather than editing `index.css` once per guess, and every other figure it prints is computed exactly the way `hero-art.mjs` computes it so the rows are comparable rather than a second opinion in different units. It exits 0 either way; `hero-art.mjs` is what gates whatever it recommends. All of them are repo-root-relative — the Bash tool's cwd persists between calls, so prefix an explicit `cd` to the repo root or the script will not resolve.

**`keycheck.mjs` is the other half of `parity4.mjs`, and neither substitutes for it.** parity4 asks whether every key that *exists* is translated eight ways. keycheck asks whether every key the code *asks for* exists. So parity4 is structurally blind to a `t('mony.left')` typo — the key is absent from all eight dicts equally, which is perfect parity — and keycheck is blind to a key present in `en` and missing from `ta`. Both are zero-dependency and need no server.

It exits 1 on three classes, which fail in three different ways:

| Class | What it is | How it fails without this check |
|---|---|---|
| `leaked` | a string literal in `frontend/src` whose prefix is a real dictionary prefix but whose full text is not a defined key | `t()`'s last fallback is the key itself, so the literal `money.leftt` renders on the page |
| `untranslated` | a translation code a Python service or `schemes.json` emits that no dictionary defines | `tBackend()` falls back to the English sentence, so the page is silently English in all 8 languages with nothing reporting it |
| `unmapped` | a scheme `category` or `level` value with no entry in `backendText.js`'s maps | prints the title-cased enum instead of a translated label |

Keying on the *prefix set* rather than on a regex is what holds its false-positive rate at zero: a CSS class, a URL and a file path do not share a prefix with the dictionary. Two things it reports as information rather than as failures, and both need a human: the keys built by interpolation (`` `lvl.${...}` ``, `` `lvlnote.${...}` ``, `` `sdata.${...}` `` in `backendText.js`), which it cannot resolve statically; and keys defined but referenced by neither side, which is currently 7 and is dead weight rather than a defect.

**Redirect a driver's output to a file rather than piping it through `head`.** `node x.mjs | head -100` closes the pipe, node takes SIGPIPE and dies **before its final `writeFileSync`** — so `report.json` silently keeps the *previous* run's data while the console shows the current one. That combination cost real time: the analysis was of run 1 while the eyes were on run 2.

**`refresh-cases.mjs` exists because the fixtures go stale silently.** `drive.mjs` seeds `sessionStorage` from three captured `case_*.json` responses, and those snapshots sat at 2 schemes with no `level` and no translation codes long after `schemes.json` grew to 30 and the services started emitting codes — so the driver kept passing while telling you nothing about the scheme UI. `refresh-cases.mjs` re-POSTs the same payload `FinancePage.jsx` builds and rewrites the three files. **Run it after any change to the services, the schemas or `schemes.json`.**

Four form cases, and **the fourth is the one that finds bugs**: `good` (tailoring/UP/Lucknow, everything populated — 14 schemes across 6 tiers), `nulls` (zero investment and a negative surplus, so `estimated_roi_percent` and `pressure_ratio_percent` both come back `null`), `empty` (a typed-in "Photography" in Delhi — no schemes, no market row; it was agriculture-in-Delhi until that started matching 12), and `blank` (**nothing entered at all**). `blank` exists because the form pages compute live previews from `Number(field) || 0`, so an unanswered question arrives as a real `0` and every derived figure reads as good news — "₹30,000 left each month", "you have enough of your planned investment" — before the user has said anything. Four bugs of exactly that class were live on `/finance`. The blank pass asserts no `₹0` and no reassurance copy survives an empty form; an all-zeros case is **not** a substitute, because a typed 0 must still print as ₹0.

`glyph-audit.mjs` flags decorative emoji and arrows rendered as bare JSX text with no `aria-hidden` ancestor. It skips glyphs inside string literals of **either** quote style — those are `icon=` props whose consumer already wraps them — and reports a glyph alone on its own line separately, since it cannot see a wrapper opened on the line above. Expect exactly 3 such hits (`App.jsx`, `AdvisoryPage.jsx`, `AnalysisPage.jsx` empty-state icons); all three have `aria-hidden` on the parent div.

**`mobile-audit.mjs` is the phone equivalent, and it is a different tool from `drive.mjs`, not a wider version of it.** `drive.mjs` asks "did the right text render"; this one asks "can a thumb use it". It emulates 360 / 390 / 412 CSS px with `Emulation.setDeviceMetricsOverride({mobile: true, deviceScaleFactor: 2})` plus touch emulation — **`mobile: true` is the load-bearing part**, because without it the viewport meta tag never applies and every measurement is a desktop measurement in a narrow window. It seeds `sessionStorage` from `case_good.json`, walks all 10 routes × 3 widths, writes PNGs and `report.json`, and exits 1 on any finding. Four classes:

| Class | Test | Why it is a defect |
|---|---|---|
| `OVERFLOW` | `documentElement.scrollWidth > clientWidth` | The page scrolls sideways: content sits off-screen and the layout jitters under a thumb. Worst mobile defect there is. It also names the widest offending elements — "the page is 73px too wide" is useless without knowing what did it. |
| `TAP` | interactive element under 44×44 | Below that a user misses and re-taps; on a form page that means abandoning the journey. |
| `TINY` | leaf text under 12px | The audience is low-literacy readers. |
| `CLIP` | `el.scrollWidth > el.clientWidth` with a non-scrolling `overflow-x` | A long unbroken word — a district name, a scheme name, a typed email — pushing out of its card. |
| `SPLIT-FIGURE` | an element whose entire text matches `/^₹\s?[\d,]+(\.\d+)?$/` occupying more than one line box | `₹30,000` wrapped as `₹30,00` / `0` is not cosmetic — the reader parses a different number. **Every other check passes on it**: nothing overflows, nothing is clipped, all the text is present. |

Four exclusions in the probe are deliberate; re-adding them just floods the output with noise that is not wrong. `.sr-only` is a deliberately clipped 1px box, so it reported `CLIP` on every page. Anything inside an ancestor whose computed `overflow-x` is `auto`/`scroll` is scrolled-out content, not overflow — `.ui-navbar-inner` scrolls on purpose, so without this every nav link reported `OVERFLOW`. An element entirely off the left edge (`right <= 0`) is the standard skip-link parking spot: it cannot widen the document and cannot be seen. And **`.ui-unit-chart` spans are exempt from `CLIP`**: the coin box is sized in `rem` on purpose, decoupled from the glyph's `font-size`, so an empty slot's ring and a filled coin stay the same size — but an emoji's advance width is ~1.28em, so at the largest text scale the glyph measures ~2px wider than its `1.6rem` box. It overhangs a *transparent* border with `overflow` visible, so nothing is actually hidden; sizing the box to the glyph instead would grow every coin and re-couple the two.

The probe **measures used values rather than reading CSS**, because a rule can look correct and still lose to the cascade. One measurement trap cost real time and is worth not rediscovering: **`el.getClientRects()` returns one rect per line box only for `inline` elements.** On a block or flex box it returns a single rect however many lines the text wrapped to — so the first `SPLIT-FIGURE` check reported 0 problems, twice, on output that was visibly broken. Use `document.createRange()` + `selectNodeContents(el)` and count distinct rounded `top` values; a Range reports line boxes either way. The general lesson: **when a new check reports zero, break the thing it watches on purpose and confirm it fires** before believing it.

Two gotchas cost real time and are both handled in the script — don't undo them. `--user-data-dir` **must be absolute**: a relative path silently attaches to the already-running Edge profile and exits with no debug port. And you must create your own target (`/json/version` → `webSocketDebuggerUrl` → `Target.createTarget` → `Target.attachToTarget({flatten: true})`, then pass `sessionId` on every command) rather than taking the first `type === 'page'` from `/json/list`, which on a signed-in profile is `edge://sync-confirmation-dialog/`. Use `http://localhost:5173` — **Vite binds `[::1]` only**, so `127.0.0.1:5173` refuses.

**`hero-art.mjs` and `brand-mark.mjs` both exist because a colour that is *computed from tokens* cannot be checked by reading `index.css`.** In both cases the value on the page is a `var()` indirection that resolves differently per theme, so the rule looks right in every mode and is wrong in one of them — and lint, build, parity and `drive.mjs` all pass either way, because the text is all present.

- `hero-art.mjs` measures the landing backdrop: mean ΔL\* of the artwork band against the page, what percentage of it clears the visibility floor, and the **contrast ratio of the hero copy sitting on top of it**, because those two constraints pull in opposite directions and the pass has to satisfy both at once. **A zero `--landing-art-opacity` is a failure now, not a mode.** It used to be a fourth mode — high contrast set the opacity to `0` on purpose, so that mode was checked on the opposite assertion — and with high contrast gone the `artOff` guard would have been a licence to skip every assertion in the script, so it was inverted rather than deleted. **It reads the image out of the computed `background-image` rather than naming a file**, mirrors `background-size: cover` over the hero's own box, and tracks **both** luminance extremes — see the backdrop-swap entry in the 8 Sept list for why each of those three was a way it could have kept passing while measuring the wrong thing.
- **`art-contrast.mjs` is retired and now exits 2 rather than printing numbers.** It modelled `town-consulting.svg` specifically — that file's per-element alphas and the `softTop` mask stops are transcribed into the script — so it became worthless when the backdrop changed, and *worse* than worthless, because it would have kept printing confident figures about an image nobody sees. It compares `.ui-hero::before`'s `url()` in `index.css` against the file it models and refuses if they differ. The raster equivalent of its modelling lives in `hero-art.mjs`, which measures the real composite instead.
- `brand-mark.mjs` rasterises the **live** SVG at 8× over the surface it actually sits on, in both themes (four mode combinations until high contrast was removed). Two notes on the technique. It cannot just point an `<img>` at the source: **an `<img>` from a `data:image/svg+xml` URL is a separate document and cannot see the host page's custom properties**, so every `var()` would fall back to nothing — the script serialises a clone with the computed `--mark-*` values inlined via `clone.setAttribute("style", vars)`. And `pctInk` alone is not enough: if the petals ever resolve to one flat fill, ink coverage looks perfect while the flower has collapsed into one blob. `worstEdge` — the smallest ΔL\* between adjacent painted runs along the horizontal centre line — is the check that catches that, and `regions` counts how many distinct shapes that line crosses (13 in both themes; the removed high-contrast mode was down to 7, which is what the check was written for and why it outlives it).

**`lang-layout.mjs` asks the one question no other verifier can: does switching language change the *layout*, not just the words?** Every other script fixes one language and varies something else. This one varies the language across all eight at **two desktop widths** (1440 and 1280) over 6 routes — **96 page loads** — and compares each page's geometry against **English at the same width**. Baselines are keyed `route@width`; keying on route alone made every 1280 load report a shift against a 1440 English page, which is true and useless. Findings: `SHIFT` (a chrome container's left edge or width differs from English — all of them are `width: min(1180px, 100% - 32px); margin: auto`, so they must be pixel-identical in every language), `NAV-CUT`, `FLUSH` (two adjacent flex children with no gap), `CLIP`, `VCLIP`, `HSCROLL`, `RAGGED`. Leading and nav-row counts are reported as information, not findings — see below for why.

**`SHIFT` has three arms and only two of them apply everywhere.** `dx` and `dw` are checked on every chrome container at 1px, because a centred fixed-width panel has no legitimate reason to move. **`dh` is checked at 12px and skipped for the containers whose height is driven by COPY rather than by layout** — `.ui-main` (the page itself), `.ui-navbar-inner` (allowed to wrap to a second row in a long script) and, as of 11 Sept 2026, **`.ui-footer-inner`**. The footer was missing from that list from the day the list was written, and the omission surfaced as **24 findings** — ta and ml, both widths, all 6 routes, `dx=0 dw=0 dh=22.9` every time. Three things about how it was settled are the transferable part:

- **It was attributed before it was fixed, by stashing rather than by reasoning.** `git stash push` → re-run → the pre-change app produced the *byte-identical* 24 findings → `git stash pop`. My reasoning said a masthead change could not touch the footer; the stash *proved* it, and reasoning is not evidence about a cascade.
- **Then it was measured, because "exclude it" and "fix it" look identical from the report.** A one-off probe on port **9369** (the number this file keeps free for exactly this) dumped every footer column's height and every text element's line-box count per language: `.ui-footer-inner` is en **101.3px** vs ta/ml **124.2px**, all three columns uniformly tall in each (53.3 / 76.2), `display: grid` with `align-items: normal` so items stretch, the element set **identical** in all three languages — and the growth is entirely that ta's tagline wraps 1 → 2 lines (22.8 → 45.7px) while ml's journey-link list does. 124.2 − 101.3 = **22.9px = exactly one line of Indic text.** That is the language, not the layout.
- **The exclusion does not weaken the gate**, and this is the check to make before adding to that list. The horizontal arms still apply to the footer unchanged, and they are what SHIFT is *for*. The footer's own height-shaped defect class — three columns starting their text on three different lines, which is the defect that was actually reported on 9 Sept — is owned by `text-align.mjs`, which fires 30 findings on it under `--broken`. So nothing is now unguarded.

The general shape: **a threshold-based arm on a copy-driven measurement is a time bomb, not a check.** It passes until a translator writes a slightly longer sentence, and then it fails somewhere unrelated to whatever you were editing.

It found two real defects and disproved two hypotheses. **Both non-findings are worth keeping written down, because each looks like a bug from the screenshots:**

- **Tight leading is not a language defect.** Tamil, Malayalam and Kannada stack vowel signs above and below the base glyph, so the natural line height is far taller than Latin's, and a `line-height` tuned on English should crop them. Measured: it fires 24× per route — but **identically in all 8 languages including English**, so it is a uniform deliberate typographic choice, not something translation broke. "Fixing" it would restyle English. Demoted to `out.leading`.
- **`RAGGED` cannot fire on this layout.** CSS grid items stretch by default (`align-items: normal`), so rows are uniformly tall by construction. Verified the check works by forcing `align-items: start` on a real grid (184px spread in English, 203 in Tamil) — kept because it is cheap and guards against someone adding `items-start` later.
- **The utility strip does not wrap differently per language.** The dialect dropdown appears for Tamil, Malayalam, Kannada and Telugu and not for English, so a narrower laptop could have tipped it into a second row and moved every section below it. Measured 34px in all 8 languages at both widths — **on 8 Sept 2026, when the wordmark still shared that strip**, so treat the 34 as history rather than as the current height. What the hypothesis actually claimed is still gated: `lang-layout` compares every chrome container against English at the same width and passes, so the strip does not differ per language whatever it now measures. Hypothesis disproved, not a fix.
- **Chrome containers do not shift horizontally at all** — `dx = 0`, `dw = 0`, no `HSCROLL`, no `CLIP`, in any language. So the "shift" the eye picks up on the landing page is **vertical growth from longer copy** (`docHeight`: en 1592, ta 1816, ml 1781, te/kn 1664), which is inherent to translation and not a defect.

**Two measurement traps in this script, both of which produced a confident zero.** They are the same failure class as the `getClientRects()` one above and cost the same kind of time:

- **`getComputedStyle().font` carries line-height.** It serialises as `700 12.5px/20px "Noto Sans"`, so assigning the shorthand to a measuring probe silently replaced its `line-height: normal` with the page's own value — every comparison became the page's line-height against itself, and the deficit was exactly 0 on all 48 loads. Set the longhands (`fontFamily`, `fontSize`, `fontWeight`, `fontStyle`) and `lineHeight = "normal"` explicitly.
- **An *inline* element's `getBoundingClientRect()` height comes from the element's primary font's content area, not the fallback font that actually drew the glyphs.** So a Tamil string measured identically to a Latin one. `display: inline-block` makes the height the real line box. Related: Chromium derives `line-height: normal` from the primary font strut, so **a font-metric check cannot discriminate between scripts in this stack at all** — cramped Indic marks are a question for the rendered PNGs, not for metrics.

Also: my own `FLUSH` probe was provably wrong on first run. Its "does this element paint" filter required own-text-or-a-background, which **skips every wrapper div — exactly the shape that collides** (a two-line heading block beside a fixed square badge). It reported 96 findings that were all the deliberate `A－/A/A＋` segmented control and missed the real collision. The filter now accepts an element with descendant text, and excludes `.ui-textsize` explicitly.

**`field-align.mjs` asks whether two form controls sharing a grid row start on the same line** — the one question none of the others cover. `drive.mjs` asks whether the right text rendered; `mobile-audit` asks whether a thumb can use it; `lang-layout` compares the *chrome's* geometry against English. None of them look inside a form's grid. Four findings: `MISALIGN` (two controls in one row more than 1.5px apart, reported with how many lines each question took), `ORPHAN` (a `.ui-required` asterisk that did not stay with the last word of its question), `PREFIX` (the `₹` more than 2px off its box's centre, or outside the padding reserved for it), `NOT-FLEX`. Modes: the default 8-language × {1440, 900, 900-lg} × 4-route matrix (96 loads), `--sweep[=lo:hi]` (4px steps across the responsive band on `/business`), `--case=lang:width[:size]` for a single load, and **`--broken`, which puts the defect back at runtime and must fail.**

Three things it taught, all of which cost time:

- **Viewport width is a blunt instrument on these pages.** Every form sits in a `max-w-4xl` section, so 1440, 1180 and 1000 all produce the *same* 896px section and byte-identical line breaking. My first `--broken` run reported **ORPHAN 0 of 56 loads** because of this — the check was inert, not clean. Only the text scale and widths below ~930px (while still above the 640px `sm:` breakpoint) move where a question wraps, and ORPHAN needs a band a few pixels wide that three arbitrary widths will miss. Hence the fine `--sweep`. This is the same lesson as the `getClientRects()` one: **when a new check reports zero, break the thing it watches on purpose and confirm it fires.**
- **It reports `unevenRows` as an instrument check.** If every paired row in a run had questions of equal height then MISALIGN was never given anything to catch and a clean result says nothing. The script warns when that count is zero. The fix was verified against 68 uneven rows in the sweep and 10 in the matrix.
- **Measure the control, never the wrapper.** A `.ui-money-field` wrapper's top sits 8px above its input's, so comparing wrappers against plain inputs compares two different things and reports a shift that is not on the screen.

**`hero-geom.mjs` asks where the backdrop's edge sits relative to the content sitting on it** — not whether the artwork is visible (`hero-art.mjs`) and not whether the page scrolls sideways (`mobile-audit.mjs`), but whether a hero child's border lands *on* the photo's border. That was the reported defect on 8 Sept 2026 and none of the other nine could see it: every text check passed, nothing overflowed, and the contrast figures were fine. It reports, per width, the `.ui-main` box, the `.ui-hero` box and its computed padding, the `::before` inset and resolved artwork box, the radius **as a percentage of the panel width**, `scrollWidth` vs `clientWidth`, and every hero child's gap to all four artwork edges. Six cases: 1440 / 1280 / 1024 / 800 desktop-ish, plus `phone-390` and `phone-360-hi` (dark + Hindi) with `mobile: true`.

Two things it settled that are worth keeping:

- **A pseudo-element has no node, so its box cannot be measured with `getBoundingClientRect()`.** It is derived from the host's rect plus the four *resolved* computed `inset` values, which is also why the technique stays correct once those insets stop being `0`. Reading `inset: 0` out of `index.css` and concluding "the artwork box is the section box" happens to be true today and would silently stop being true.
- **It overturned my own eyeball reading of the screenshot.** From the capture I estimated the left gap at ~2px and the card's right gap at ~38px, and started reasoning about an asymmetric artwork box. Measured, both were **exactly 0** at every width — the difference was an artefact of the scaled crop. The measurement is authoritative; the screenshot is for spotting that something is wrong, not for deciding what.

**`print-audit.mjs` is the only script that measures the print stylesheet at all.** Every other verifier here measures the screen, and `@media print` is a different stylesheet that no amount of screen measurement exercises — before this it had been "verified" only by reading `index.css`, which tells you what the author intended. The technique is `Emulation.setEmulatedMedia({media: 'print'})`, which swaps the engine's media evaluation with no print dialog, and then ordinary `getBoundingClientRect` / `getComputedStyle`: an element the print block hides measures 0×0, one it failed to hide measures its real box. Three cases — `/report` in light and dark plus `/analysis` in light. It was five, `/report` in all four mode combinations, until high contrast was removed; the reset still has to undo each surviving mode, and the *specificity of the rule it undoes differs between them*.

Each of its three checks found a real defect the first time it ran, and all three are the same shape — **a rule that looks correct and matches nothing**:

- `DETAILS` — the block hides `.ui-disclosure > summary` and sets `.ui-disclosure-body { display: grid !important }`, intending to force a collapsed `<details>` open so the detailed figures reach the PDF. **A closed `<details>` is not opened by a `display` rule on its children.** Chromium's UA stylesheet puts `content-visibility: hidden` on the `::details-content` pseudo-element wrapping them, and no `display` declaration on a descendant defeats that — the descendant is not laid out at all, and `!important` does not help because it is not fighting a `display` rule. The figures silently vanished from the printed page.
- `CHROME` — the block hid `.ui-footer` and `.ui-topbar`, **neither of which any element in the app carries**. The footer is `.ui-footer-gov` + `.ui-footer-bottom`, the masthead is `.ui-masthead`. Both were live rules styling nothing, so the selector list read complete while the lotus mark, the tricolour band and the whole government footer printed onto the sheet. The script now reports a listed class matching no element as a dead rule, which is what would have caught it.
- `TOKENS` / `PAPER` — **`@media print` adds no specificity**, so every selector in the token-reset list has to out-specify the screen rule it is undoing. Three of them are `(0,1,0)` and win on source order, but `[data-contrast="high"][data-theme="dark"]` was `(0,2,0)` and beat all three: dark + high contrast printed `--color-bg: #000000` and `--color-text: #ffffff`, a **white-ink-on-black page**, on the one sheet a user physically carries to a bank. Fixing it meant listing that pair explicitly, because **a compound selector is not redundant with its own parts.** High contrast is gone and the pair with it, but the lesson is kept as a comment in `index.css` and in `print-audit.mjs`, because it applies to any two presentation attributes that can be set at once.

**The print token reset is the whole palette on purpose, and this is the second time that list has been incomplete in exactly the same way.** First the `--mark-*` set had to be restated (a `#FFE000` logo invisible on white paper); then six colour tokens turned out to be uncovered, of which two draw on the sheet — `--color-danger` is the shortfall figure in the money grid and the `.ui-bar-value.is-bad` figure in the charts, and from a dark laptop it printed `#FFB4AB` at **1.70:1 on white**, i.e. a number the reader cannot make out; `--color-success` fills the "good" bar and printed `#7CD9A5`, all but gone, while the red bar beside it still showed. Both times the uncovered tokens were "the ones nothing on `/report` happens to draw with", right up until something did. So the list is exhaustive rather than curated, and the script asserts it:

- **The strong check is invariance, not contrast.** Under `media: print` the sheet must not depend on the laptop's theme at all, so **every palette token must resolve to the same paint in every mode**. It is exact, threshold-free, cannot produce a false positive, and fails on a token the reset *forgets* rather than on one it mishandles — which is the failure this block actually has. Proven by deleting the two tokens on purpose: 8 findings, and the invariance arm caught high-contrast-light's `#8A0000` that the contrast arm passes.
- **A contrast floor applies only to tokens that draw TEXT.** `--color-danger` gets a 4.5:1 floor against the paper *this case actually resolved* — not against an assumed white, so a regression in the surface reset cannot quietly make it pass. Fills get no floor: the amber warn bar is 1.7:1 on white by design and reads as a bar because the track is bordered and the figure is printed beside it, so a floor there would report the design rather than a defect.
- **`getPropertyValue` on a custom property returns the raw token TEXT** — `#FFB4AB`, or a whole `var()` chain for the `--mark-*` set — which the luminance maths cannot read and which compares unequal across modes for reasons that are not about the colour. Assign it to a probe element's `color` and read it back: always `rgb(r, g, b)`, which both compares and measures. Same principle as the mark check asserting on the resolved `fill` rather than on the token name.
- **The probe string is a template literal, so a backtick anywhere inside it — including in a comment — closes it early.** The file says so and I still did it; the tail then reparses as a *tagged* template on whatever identifier precedes it, and the failure surfaces as `SyntaxError: Unexpected identifier` on a comment line.

**A filter maths trap worth not rediscovering, from the landing backdrop.** Shorthand CSS filters operate in sRGB, and `brightness(b)` followed by `contrast(k)` composes to `v·b·k + 0.5(1−k)`. So **`contrast(k > 1)` pushes everything above mid-grey toward white** — exactly backwards when the problem is that a light palette is already too close to a near-white page. `saturate()` is the cheap lever: it barely moves luminance, so it buys colour without spending any of the contrast budget. The light-mode pass ended at `brightness(0.5) saturate(2.2) contrast(0.91)` at opacity `0.5`.

The same maths carried straight over to the JPEG backdrop, and one corollary is worth stating outright because it reads as a typo: **`contrast(0.91)` is there for accessibility, not for looks.** Below 1 it pulls everything toward mid-grey, which *lifts the black halftone off zero* and hands the hero text back contrast — 5.18:1 → 5.48:1 on the worst pixel, for 0.5 ΔL\* of visibility. And because `saturate` is measurably neutral on both constraints, its value is the one number in that filter chain that may legitimately be chosen by eye; it went `2.2` → `1.2` when the backdrop changed, purely because 2.2 existed to stop halved brightness reading as a grey smudge on pale line art and lands lurid on an already-colourful photo.

**The scripts live in `tools/` and are version-controlled; `screenshots/` is gitignored and holds only their output.** That split was made on 9 Sept 2026 and the reason is the ratio: `screenshots/` is **8.1 GB** — Edge profile directories and thousands of PNGs — while the scripts inside it totalled **317 KB**. So a teammate who cloned the repo got the app and none of the gates, and the obvious fix of relaxing `.gitignore` in place was the dangerous one: git does not descend into an excluded directory, so a naive `!screenshots/**/*.mjs` re-include does nothing, and a pattern that *does* work is one typo away from committing gigabytes of browser profile data to a shared repo — permanently, since the blobs stay in history after any follow-up delete.

Two mechanical facts made the move safe, and both were verified rather than assumed:

- **Every script but one resolves paths against `process.cwd()`**, not against its own location — `resolve('screenshots/verify/out')` and friends. So moving the file changes nothing as long as it is still invoked from the repo root, which was already the documented requirement.
- **`glyph-audit.mjs` is the exception** and it survives by arithmetic rather than by luck: line 17 is `new URL('../../frontend/src/', import.meta.url)`, and `tools/verify/` is the **same two levels deep** as `screenshots/verify/` was. Any future move to a different depth breaks that one line, and nothing else in the suite.

**A third fact was checked and turned out to be false, and it broke the suite on a fresh clone for two hours.** `refresh-cases.mjs` wrote `screenshots/verify/case_*.json` with **no `mkdirSync`** — correct for as long as it *lived* in the directory it writes to, because the directory was then guaranteed to exist. Moving it out removed that guarantee, and **nothing under `screenshots/` is tracked** (`git ls-files screenshots` → 0), so on a fresh clone the target directory does not exist and `writeFileSync` throws `ENOENT`. Reproduced in a temp dir before fixing, and fixed with `mkdirSync('screenshots/verify', {recursive: true})` — `recursive` also making it idempotent across the cases.

Three things about it are worth keeping:

- **It was the worst-placed possible instance.** `refresh-cases.mjs` is the *first* script a new teammate has to run, because the fixtures are deliberately untracked, and **five of the sixteen browser gates read those fixtures** — `drive` (the main gate), `lang-layout`, `mobile-audit`, `motion-audit`, `print-audit`. So one missing `mkdirSync` took out five gates plus the script that feeds them, and the four server-free gates passing gave no hint of it.
- **The audit that finds this class is one line**, and it is worth re-running after any script move: compare `grep -c writeFileSync` against `grep -c mkdirSync` per file. Every other writing script already had 2–4 `mkdirSync` calls; this one had zero. (`merge-err-keys.mjs` also has zero and is *correct* — it overwrites `frontend/src/i18n/strings.js`, whose parent is tracked and therefore always exists. The check needs a human to read the target, not just the count.)
- **A script that lives in its own output directory hides this dependency completely.** That is the general trap, and it is the same shape as `art-contrast.mjs` modelling one specific SVG: the code is correct in place and silently wrong once its surroundings change, with nothing in the file itself to indicate which.

The 20 stale `node screenshots/…` invocation comments inside the scripts were rewritten in the same pass, anchored on `\.mjs` so output paths were untouched — and 4 of the 21 files came back modified with **zero content change**, because `sed -i` rewrote them with different line endings while matching nothing. Those were restored rather than committed; on Windows with no `.gitattributes`, a bulk `sed` over files it does not match is line-ending churn, and `git status` shows it while `git diff` does not.

The scripts still *write* into `screenshots/`, which is why that directory keeps its ignore rule rather than being deleted. Kill Edge and both servers when done.

  - **Deleted:** every `[data-contrast="high"]` rule in `index.css` (verified zero `data-contrast` in the built CSS), `ContrastToggle()` and its call site in `App.jsx`, and `common.highContrast` from all 8 dictionaries. `sih-contrast` may still sit in a returning visitor's `localStorage`; nothing reads it, so it is inert rather than a bug.
  - **`man.tipText` was rewritten in all 8 languages, not deleted.** Its third tip named the contrast control, and the string is live manual copy rather than a dead key — so each language's tip now points at the theme toggle, using that language's own existing word for the dark look. This is the layer where a naive grep-and-delete would have broken visible text.
  - **`hero-art.mjs`'s `artOff` guard was inverted, not dropped** — the same move as `manual-audit.mjs`'s PILL check. It prefixed three assertions with `!artOff &&`, which was correct only while high contrast deliberately set `--landing-art-opacity: 0`; with the mode gone it became a licence to skip every assertion in the script, so one stray zero would have had all three modes printing "artwork off, as intended". A zero opacity is now a failure. Mode counts fell with the mode: `brand-mark` 4 → 2, `hero-art` 4 → 3, `manual-audit` 5 → 3, `print-audit` 5 → 3, and `mobile-audit`'s `360-stress` lost its HC arm. `print-audit`'s `report-dark` picked up `lang: 'hi'` so the Hindi coverage the dropped `report-dark-hc` carried did not go with it.
  - **`print-audit.mjs`'s brand-mark check turned out to have been inert since it was written**, found while trimming its cases. It asserted the petals do not print `#FFE000`, but **`getComputedStyle(el).fill` on a gradient-filled element returns `url("#markr0")`, not a colour** — so the regex could never match. The paints that *do* resolve are the gradient's `<stop>` elements (they carry `style={{stopColor: 'var(--mark-petal-*)'}}`) and the coin ring's plain `fill`, and the check now reads those. It asserts on the **best** paint, not every paint: **WCAG 1.4.11 exempts logotypes from contrast requirements**, and a designed gold→orange gradient legitimately has a 1.66:1 inner stop, so a per-paint 3:1 rule fails the shipping mark. The real invariant is that the mark is visible *at all* — which is exactly what the `#FFE000` collapse broke, since it took every paint to 1.07:1. Verified by injecting `#FFE000` into `@media print` on purpose (exit 1, 3 findings) and restoring byte-identical.

Deliberately **not** added, so these don't get proposed as oversights: no charting library, no i18n library, no localStorage for financial answers, no route guards, no frontend test framework. (Backend translation *was* on this list and is now built — see the translation-code section.)

### The 9 Sept 2026 optimization pass

On the brief "optimize the entire MVP without compromising with any functions, features, the UI/UX, backend, database, schemes, images, documents". **The binding half of that sentence is the second one**, so every change here is output-*identical* rather than merely test-passing, and the section is organised around how that was proven rather than around what got faster.

**Read this before optimizing anything else here: two of my three starting hypotheses were wrong, and measuring is what showed it.** I expected the 1 MB JS bundle's parse/execute and the `merge()` call in `strings.js` to be the frontend's startup cost. Measured, `DOMContentLoaded` was 66 ms desktop on a cold cache, and **`merge()` is 0.2–6.4 ms** — the bundle is mostly *string data*, which parses far faster per byte than code does. There was no startup problem of the kind I assumed. The real backend cost was somewhere I had not looked at all: **re-reading and re-parsing 55 KB of JSON from disk on every single request**, 0.18 ms of a 0.40 ms pipeline, i.e. 45% of the whole thing and more than every arithmetic service in the app put together.

**Backend — `run_unified_analysis` 0.401 ms → 0.048 ms (8.4×).** Three files, and the shape of all three is *derive once what depends only on the data file*:

| | before | after | |
|---|---|---|---|
| `run_unified_analysis` | 0.401 ms | **0.048 ms** | 8.4× |
| `match_schemes` | 0.279 ms | 0.043 ms | 6.5× |
| `get_market_context` | 0.080 ms | 0.001 ms | 80× |
| test suite | ~0.73 s | 0.56 s | — |

- **`load_json` is `@lru_cache(maxsize=None)`.** The cache never expires, which is correct here and would not be in general: nothing writes these files at runtime, and editing one during development restarts uvicorn (`--reload` does it), which drops the cache with the process. `clear_data_cache()` exists for a test or script that rewrites a data file *inside* a running process — and it clears the two derived indexes as well, since those are built from what `load_json` returns and would otherwise still describe the old file.
- **`_scheme_index()` and `_market_index()` pre-lowercase the fields the lookups compare on**, once per process instead of once per row per request. `_market_index` also collapsed a two-pass search into one: the old code re-scanned and re-lowercased every row when no district row was found, which is the *common* case, so the fallback path paid double.
- **THE ONE HAZARD, and it is the reason the tests exist.** `lru_cache` on a function returning a mutable list makes the returned object **shared** — every caller gets the same list, so a caller that mutates it corrupts the data for every later request in the process, and it corrupts it **silently**: the file on disk is still correct and a restart makes the symptom vanish. No service does mutate it (`market_service` builds a fresh dict per row with `{**row}`, `scheme_service` copies the lists it puts into a response), and `test_a_response_cannot_poison_the_cached_scheme_dataset` / `test_a_response_cannot_poison_the_cached_market_rows` pin that, one per data file. **Treat what `load_json` returns as read-only**, and if you add a service that touches it, add the third test.
- **`serves_state` and `serves_location` look identical and must not be merged.** They differ deliberately on an empty *user* value — see the Formulas section. The optimized `_state_is_served` / `_location_is_served` keep that asymmetry.
- **`categories` stays an ordered tuple while `states` and `locations` became frozensets.** The matcher's direction is `if scheme_category in phrase` — a substring test against the user's typed phrase, not a set membership test — so a frozenset there would silently change what matches.

**Equivalence was proven by sweep, not by the suite passing.** The old and new implementations were run side by side over **7,200 input combinations** and asserted byte-identical, and `refresh-cases.mjs` then re-POSTed the real `/finance` payload against the live optimized backend: 14 schemes, scores [100, 90], 1 market row at `district`, 6 tiers — matching the figures already documented under "Safest demo configuration" exactly. **171 tests** now (was 169).

**Frontend — one 1,018 kB chunk became seven, and `DOMContentLoaded` fell 19–31%.** The full reasoning is in a long comment in [vite.config.js](frontend/vite.config.js); what matters here is the four things that make it safe and the one that makes it worth doing:

| | 1 chunk | 7 chunks |
|---|---|---|
| largest chunk | 1,018.74 kB | **304.86 kB** |
| total gzip (JS) | 233.61 kB | **233.12 kB** |
| DCL desktop | 66.2 ms (65–80) | **48.0 ms (44–55)** −27% |
| DCL mid-phone 4× | 202.7 ms (186–218) | **139.1 ms (130–146)** −31% |
| DCL low-phone 8× | 487.4 ms (453–507) | **393.6 ms (368–412)** −19% |
| Vite 500 kB warning | yes | **gone** |

- **The ranges do not overlap at any tier**, which is what makes this an effect rather than noise, and **the win grows with how slow the device is** — the direction that matters for the audience.
- **Total gzip went DOWN**, which is worth recording because the obvious objection to splitting *these particular* files is that gzip compresses each stream separately and should lose the cross-file redundancy between eight Indic dictionaries. Measured, it does not: each chunk is more internally homogeneous than the concatenation was, and that pays for the extra boilerplate. It costs +1.3 kB over the wire in total.
- **NOTHING IS LAZY.** Every group is still a static import, so the module graph, the execution order and the behaviour are exactly what they were — this changes only how the same modules are packaged. That is what made it safe two days before the round.
- **Per-language dictionary splitting is the line to hold, and this is the reason.** It is the largest remaining theoretical win (~52% of the initial payload), but the dictionaries are eight objects inside four files and **a bundler cannot split an object literal's properties** — it needs the source restructured, which breaks `parity4.mjs` and `keycheck.mjs`, both of which parse those files statically. On these measurements it buys ~20–40 ms at 8× throttle, and it risks a flash of English on the language switch, which is the strongest single moment in the demo.
- **Rolldown/Vite 8 renamed the option**: `output.advancedChunks` is deprecated in favour of `output.codeSplitting`, same `{groups: [{name, test}]}` shape.
- **Every group's `test` names its file exactly and is terminated by `\.js`.** That is not pedantry: `strings` as a loose pattern happens not to match `resultStrings.js` or `schemeStrings.js`, but **only because those spell it with a capital S** — so three groups that look like they overlap would be kept apart by nothing but the casing of a filename. (I wrote "ordered narrowest-first because the first matching test wins" in that comment first, tested it in node, and found ordering is irrelevant here. Anchoring removes the question.) Both slash classes are in each pattern because the test runs against whatever separator the platform produced, and this repo is developed on Windows.

**`@import "tailwindcss"` extracts class candidates from PROSE, not just from markup, and it scans the config files next to `package.json`.** This is the most transferable finding in the pass. Adding an explanatory comment to `vite.config.js` containing the words "still a static import" put **`.static{position:static}` into the built stylesheet** — a real utility class, generated from an English sentence, for an element that does not exist. Twenty bytes; the mechanism is the point, because any explanatory comment in any scanned file can silently emit CSS and nothing reports it. Fixed in [index.css](frontend/src/index.css) with `@import "tailwindcss" source(none)` plus two explicit `@source` rules (`../index.html`, `./**/*.{js,jsx}`), so `eslint.config.js` and `vite.config.js` are out of scope **by construction rather than by wording**. Two notes:

- It removed two *pre-existing* prose-derived classes as well — `.invisible` from a sentence in `src/assets/README.md`, `.filter` from one in `README.md`. CSS went **41.62 → 41.40 kB**.
- **Verified by diffing the built stylesheet against the auto-detected version**, not by trusting the globs: exactly three classes disappeared, all three traceable to English prose, none present in any `className=` anywhere in `src/` or `index.html`. If a utility ever goes missing, this is the first thing to check — a class used somewhere those two globs do not cover will not be generated.

**Deliberately not changed, so these don't get proposed as oversights.** `districtsForState` is a 36-entry linear scan (negligible). `coverageFor()` in `strings.js` is dead code — exported, imported nowhere — but it is documented intent and tree-shaken out of the bundle anyway. `public/town-consulting.svg` and `public/icons.svg` are unreferenced by the app but **referenced by `svgcheck.mjs` and `art-contrast.mjs`**, and ship into `dist` without ever being fetched by a browser, so they cost nothing at load. `src/assets/brand/*.png` (~1.2 MB) are never imported, so never bundled — they are the brand deliverables. And `public/hero-backdrop.jpeg` is already at ~0.22 bytes/pixel; re-encoding a halftone image risks visible artefacts *and* would shift the pixel-level figures `hero-art.mjs` gates on.

**Full verification after all of it**, because "don't compromise" is the requirement: 171 tests; `parity4` 619 keys all checks passed; `keycheck` PASS (0 leaked / 0 untranslated / 0 unmapped); `svgcheck` 5 checked 0 refused; `glyph-audit` exactly the 3 documented hits; `refresh-cases` good=14/[100,90]/1 market/6 tiers; **`drive.mjs` 36/36**; **`mobile-audit` 40/40**; `print-audit` 0 findings across 3 renders; `hero-art` 3 modes 0 problems (chip worst 5.47:1); `brand-mark` 2 modes 0 problems (regions 13, worstEdge 12.8); `manual-audit` 3 modes 0 problems, no disclaimer pill; **`lang-layout` 96/0**; **`field-align` 96/0** (worst ₹ offset 0.7px, 10 uneven rows so MISALIGN had something to catch).

### The 9 Sept 2026 motion layer

On the brief "add some light-weight animations … will it hamper the light-weight criteria". **The answer to the second half is +170 bytes of gzipped CSS and zero JS**, so the section is organised around the traps rather than around the effect.

Three tokens in `:root`, ten eased transitions, a press on `Button`, two hover states on controls that had none — and a `prefers-reduced-motion` guard. `--motion-fast` 120ms, `--motion` 180ms, `--motion-ease` `cubic-bezier(0.4, 0, 0.2, 1)`, which is **Tailwind's own default ease on purpose**: eleven JSX call sites already carry the bare `transition` utility, so anything else would have the CSS and the utilities disagreeing on the same page.

| | before | after |
|---|---|---|
| CSS raw | 41.40 kB | 42.78 kB |
| CSS gzip | 8.90 kB | **9.07 kB** |
| JS | — | byte-identical, all 7 chunks |

**THE TOKENS ARE NOT OPTIONAL TO DEFINE, and this was live in the tree.** A formatter hook wrote back a copy of `index.css` predating the three `:root` definitions while keeping all ten `transition:` declarations that reference them. **An undefined custom property makes the whole declaration invalid at computed-value time** — `transition: background-color var(--motion-fast) var(--motion-ease)` does *not* fall back to a default duration, it **disappears**, and `transition-property` reverts to its initial `all` with `transition-duration: 0s`. So every control snapped, the `var()` sat in the built stylesheet looking perfectly correct, `eslint` exited 0, `vite build` exited 0, and **every single browser verifier passed.**

**That is because no verifier in the suite could observe motion at all**, which is the transferable finding here. Not one of the twelve that existed then called `getAnimations()`, read `transition-duration` or `transition-property`, sampled two frames, or enabled the CDP Animation domain — they all measure a page at rest, so a transition that silently no-ops produces a **byte-identical `report.json`** to one that runs. `motion-audit.mjs` (port 9365) closes it. It reads the tokens *the way the browser uses them* — assigning `var(--token)` to a real property on a probe and reading the computed longhand back, because `getPropertyValue` on a custom property returns the raw token **text** and so reports a dead token as present. Then it asserts each target's computed property list is **exactly** what `index.css` declares (an over-broad `all` would satisfy "does it animate" while easing layout properties nobody vetted), dispatches a real `Input.dispatchMouseEvent` hover and collects `transitionrun`/`transitionstart` by listener, and re-reads everything under `Emulation.setEmulatedMedia({features: [{name: 'prefers-reduced-motion', value: 'reduce'}]})`. `--broken` puts every defect back at runtime and must exit 1; it fires ten distinct finding kinds.

**What is eased is chosen so that no other verifier's measurement can move**, which is what made this safe two days before the round. Nine of the ten are colour-only. The two that are not:

- **`.ui-bar-fill` eases `width`, and it is safe for a reason that is easy to break.** A CSS transition needs a *previous* value to interpolate from, and the width arrives inline from `Charts.jsx:43` at mount — so nothing runs on page load, only when the reader re-submits `/finance`. It is also confined to `.ui-bar-track`'s fixed 26px box with `overflow: hidden`, so it cannot reach `mobile-audit`'s OVERFLOW or `field-align`'s 1.5px tolerance. `motion-audit` asserts the load case rather than assuming it.
- **`.ui-unit-chart span` deliberately excludes `font-size`.** `font-size: 0` is what hides the empty-slot emoji, and an emoji's ~1.28em advance against a box fixed at `1.6rem` is the documented reason `mobile-audit` exempts `.ui-unit-chart` from CLIP. That exemption covers a **static** ~2px overhang; easing `font-size` would sweep the coin through every intermediate size and put a **moving** overhang inside a check that is exempt on a known constant.

`.ui-skip-link` must never be eased — `:focus` moves it from `left: -9999px` to `0`, so a keyboard user would watch the first control on the page fly in from off-canvas. It is on `motion-audit`'s forbidden list.

**The reduced-motion guard sits in `@layer base`, not unlayered, and that is load-bearing.** Cascade 5 **reverses layer order for `!important`** and treats unlayered as a final implicit layer, so **an unlayered `!important` is the *weakest* author important** — Tailwind's `!` modifier, compiled into `@layer utilities`, beats it. Measured in Edge: utilities-important 300ms against unlayered-important 0.01ms yields **300ms**; the same rule in `@layer base` yields 0.01ms. The guard is six declarations and each fails its own way:

| Declaration | Why not the obvious alternative |
|---|---|
| `transition-duration: 0.01ms` | **not `0`** — a zero duration fires no `transitionrun`/`transitionstart`/`transitionend`, hanging any JS awaiting one |
| `transition-delay: 0s` | the easily-missed one: **a delay outlives a collapsed duration**, so `opacity 300ms 200ms` still waits 200ms and then snaps |
| `animation-iteration-count: 1` | **not `animation: none`** — `none` drops `animation-fill-mode` with it, so an element whose static style is its pre-animation state stays permanently at `opacity: 0`. And `0.01ms` does **not** stop `infinite`: it re-runs thousands of times a second, i.e. a strobe, strictly worse for a photosensitive reader than the motion it replaced |
| `animation-timeline: auto` | **not `none`** — a scroll-driven animation takes progress from scroll offset, so neither duration override collapses it, and `none` means the effect never applies so fill-mode never lands |
| `animation-duration`, `scroll-behavior` | as above |

The selector is `*, *::before, *::after`. **`::backdrop`, `::marker`, `::placeholder`, `::selection` and `::details-content` are NOT covered**, and adding them to that list would be a mistake: an unrecognised pseudo-element invalidates the *whole* selector list in Firefox and Safari, so the guard would stop applying to everything. They need a separate rule.

**That table described the guard for a day before the guard matched it, and that gap is the entry worth reading here.** What actually shipped in `6015a48` was **two** declarations — `scroll-behavior` and `transition-duration` — **unlayered**, i.e. missing four of the six and sitting in the one place the paragraph above says it must not sit. `4eea091` then documented the six-in-`@layer base` version the same day, so the file described the intent while the stylesheet carried something weaker, and **nothing could tell them apart**: the two declarations that were present are the two that cover the ten transitions this app actually has, so `motion-audit`'s reduced-motion arm passed on the thin version. Hardened on 9 Sept 2026 to the six above, inside `@layer base`, verified in the *built* CSS at `layers=[base] depth=1` — which is the only place the layer assignment is observable, since Lightning CSS may hoist or merge blocks. Two transferable points: **a doc written from intent rather than from the file is indistinguishable from a doc written from the file**, and a verifier that only exercises the properties you happen to use cannot report the ones you forgot — the `animation-*` arms of this guard are still unexercised by anything in the app, so they are covered by reading, not by measurement.

**Two other things `motion-audit` found, both worth knowing:**

- **`.ui-navbar-link.is-active` had no hover response at all.** It and `.ui-navbar-link:hover` are both `(0,2,0)`, and the active rule is written **second** — so **source order** meant hovering the nav item for the page you are already on changed nothing while its eight neighbours lit up, reading as the current item being the one dead control in the bar. Fixed with `.ui-navbar-link.is-active:hover` at `rgba(255,255,255,0.2)`, brighter than both so a hovered active link stays distinguishable from a hovered inactive one.
- **`transition-property`'s initial value is `all`**, so an element with no transition whatsoever computes `all` — paired with `transition-duration: 0s`. The first version of the forbidden-list check keyed on the property name alone and reported a **false violation** on `.ui-skip-link`, which declares nothing. A violation has to be a forbidden property *with a live duration*.

**`getBoundingClientRect` returns the transformed box**, so `Button`'s `active:scale-[0.98]` press momentarily measures under `mobile-audit`'s 44px TAP floor. It is safe only because `:active` holds while the pointer is down and **no verifier presses anything** — do not put a transform on a *resting* state for that reason. (Tailwind v4 emits `scale: .98`, not `transform: scale()`.)

**Do not write a class-shaped literal in a comment anywhere under `src/`.** `index.css` uses `@import "tailwindcss" source(none)` with `@source "./**/*.{js,jsx}"`, so `src/**` **is** scanned — and the first version of the comment in `Button.jsx` named an arbitrary `transition-[…]` variant in prose, which Tailwind duly generated as a real rule for an element that does not exist. Same mechanism as the `.static` finding in the optimization pass; `source(none)` scopes *which files* are scanned, not what counts as a candidate inside them.

Deliberately **not** animated: a hover lift on the cards. `.ui-feature-card` is a non-interactive `<article>` ([App.jsx:535](frontend/src/App.jsx#L535)), not wrapped in a link, so a lift would teach a low-literacy reader that cards are tappable. No entrance/reveal animations either — they delay content for a reader on a slow phone and would move geometry under every verifier's fixed sleep.

### Every route opens at the top, 9 Sept 2026

Reported as "some of the pages open from the middle of the webpage". **The cause is that a single-page app never resets the scroll offset on its own** — react-router swaps the page component and the window keeps exactly the offset it had. Every form step's Continue button sits at the *bottom* of a tall page, so tapping it landed the next step already scrolled past its own heading; `/schemes` and `/report` were the worst, and one measured hop carried 10,812px into a page whose maximum was 1,233px, i.e. the reader landed on the footer.

`useOpenAtTop(pathname, hash)` in [App.jsx](frontend/src/App.jsx), called from `AppShell`. Four details are load-bearing:

- **`useLayoutEffect`, not `useEffect`.** A layout effect runs before the browser paints, so the new page is never *shown* at the old offset. `useEffect` runs after paint and flashes the mid-scrolled page for a frame — which is a smaller version of the same defect rather than a fix.
- **`scrollTo({top: 0, left: 0, behavior: 'instant'})`, not the two-argument `scrollTo(0, 0)`.** Both are instant today because nothing sets `scroll-behavior: smooth`, but the two-arg form *obeys* that property if anyone adds it, and an animated scroll on every navigation would move geometry under the fixed sleeps every browser verifier measures at.
- **A non-empty `location.hash` bails out.** `#how-it-works` (the landing page's "See how it works") and `#main` (the skip link) are same-page anchors that never change `pathname`, so a blanket scroll-to-top would defeat both — and it would *look* like the fix working. `scroll-audit`'s `ANCHOR` arm exists for exactly this.
- **`history.scrollRestoration = 'manual'` is not belt-and-braces.** Left on the default `'auto'`, the browser restores the previous offset on back/forward **asynchronously**, possibly after the layout effect has already run, so the defect returns through the back button with the effect fully in place. Proven by the `BACK` finding under `--broken`. Accepted consequence: a refresh now also opens at the top — the answers survive regardless, because they live in `sessionStorage`, not in the scroll position.

**No existing verifier could see this, and the reason is structural rather than an oversight.** `drive`, `mobile-audit`, `lang-layout`, `field-align`, `hero-geom` and `print-audit` all navigate by URL and measure a page loaded **cold**, i.e. at offset 0 by definition — none of them performs an in-app navigation at all, so the one code path where the offset carries over is the one path none of them exercises, and their reports are byte-identical either way. [scroll-audit.mjs](tools/verify/scroll-audit.mjs) (port 9367) closes it: **33 hops** in the order a reader performs them, plus the back button and the anchor. It began at 8 and was widened to cover every in-app control that navigates — the nav bar from each page, the four `Continue` buttons, the eight back links, the footer's journey links, the landing CTAs and the manual dialog's own exit — because 8 hops proved the *hook* and left most of the app's navigating controls unexercised. It leans on **nav-bar links** wherever it can, because a nav link works from any page and cannot be gated by a form's validation, and uses the `Continue` buttons deliberately because those are the controls the defect was reported against and sit where the source offset is largest. Its window is **1280×720 on purpose** — a taller one makes several of these pages fit entirely and every case goes inert. Findings: `TOP` (destination opened more than 4px down — the slack is for a sub-pixel settle, against a defect measured in hundreds of px), `BACK`, `ANCHOR`, `NO-CONTROL`, `NO-NAV`, and `INERT` as an **in-band instrument check** — a hop whose source page could not be scrolled at least 200px proves nothing and is reported rather than counted as a pass.

`--broken` restores the pre-fix behaviour faithfully rather than approximately: it stubs `window.scrollTo` **and** forces `scrollRestoration` back to `'auto'`, via `Page.addScriptToEvaluateOnNewDocument` rather than post-mount injection, because a layout effect cannot be patched after the mount it runs in. **The probe therefore must not scroll with `window.scrollTo` itself** — it assigns `documentElement.scrollTop`, which its own refuter cannot intercept. Clean: **33 hops all at 0px** from source offsets of 568–10,812px, back button 6,991px → 0px, anchor at 838px with the section 96px below the viewport top (`scroll-mt-24`), no inert cases. `--broken`: exit 1, **33 findings**.

**One of the 33 is over-determined, and finding that out took a dedicated probe.** The hop that leaves the instruction-manual dialog passes *with the fix removed* — which is indistinguishable from an inert case until you measure it, and the reflex reading ("the refuter is broken") is wrong. Measured: stubbing `window.scrollTo` and clicking a **plain** landing link from the same offset lands at 706px, the destination's own maximum scroll, i.e. the defect; the same stub through the dialog lands at 0. `scrollTo` was called and swallowed exactly once in both, so the refuter works. The difference is the scroll lock — `InstructionManual.jsx` restores `body.style.overflow` in a **passive effect cleanup, which runs after paint**, so during the commit that swaps `/` for `/profile` the body is still `overflow: hidden`, the viewport is momentarily not scrollable, and **Chromium resets the offset to 0 rather than clamping it to the new maximum**; the cleanup then restores `overflow` and 0 stands. Two things follow. The lock does **not** clamp at the source (measured: y stayed 985 with `bodyOverflowY: 'hidden'`), so this is a destination-side reset, not a source-side one. And that hop verifies the user-visible outcome for the app's one navigate-out-of-a-modal path while proving nothing about `useOpenAtTop` — keep it for the former, and **do not read a `--broken` run as 33-of-33 refuted**. The general rule this adds to "break the thing it watches on purpose and confirm it fires": **when a check *passes* under the refuter, find out why** — an unexplained pass is indistinguishable from an inert case.

### The funding gap counted, 23 Sept 2026 (branch `fix/advice-correctness`)

**`funding_gap` was computed and then ignored by every piece of advice.** `financial_service` has returned it since defect 4, `/report` printed it, and nothing downstream read it. What changed, by service:

| Service | Change |
|---|---|
| `risk_service.py` | the gap is priced as a new loan (`estimate_monthly_repayment`, 12% / 60 months, annuity) and added to the entered EMI; the band is taken on the total. Returns the terms (`monthly_emi`, `estimated_new_emi`, `total_monthly_emi`, the two assumptions) and `risk_level_without_new_loan`. `_REASONS` is keyed on `(band, has_new_loan)`, so a gap-driven band gets a `rsn.gap*` sentence that says the loan was counted |

- **12% over 60 months is an assumption, and the page says so.** `ch.pressureIncludesNew` ("This counts a loan for the money still needed, worked out at {rate}% a year over {years} years. ## Conventions

Match the surrounding file; the two halves of the codebase have genuinely different styles.

**Backend.** Plain module-level functions, no classes, no framework magic. Type hints on parameters, none on returns. Services return plain `dict`s. Numeric outputs are `round(x, 2)`. Routers are one file per domain with `APIRouter(prefix="/api/<domain>", tags=[...])`. Services never touch FastAPI, and routes never do arithmetic. `str | None` syntax is fine (Python 3.14).

**Frontend.** Function components, no TypeScript, no prop types. Named helper components live at the bottom of the page file that uses them (`MetricCard`, `SectionHeading`, `DetailRow`, `SummaryCard`, `MarketCard`, `MarketRow`). Formatters (`formatCurrency`, `formatPercent`, `formatText`, `hasNumber`) are duplicated per page by design. **The cost of that duplication is drift, and it has been paid twice** — first `hasNumber` (see the null-guard rule below), then the negative sign: a shortfall must print as **`-₹5,000`, sign before the symbol**, not `₹-5,000`, and the four copies did not agree. All four now do `(amount < 0 ? '-₹' : '₹') + Math.abs(amount).toLocaleString('en-IN')` — `AnalysisPage`, `AdvisoryPage`, `ReportPage` and `FinancePage`'s `rupees`. If you change one, change all four; nothing checks. Colors always go through `var(--color-*)`, never literal hex. `ReportPage.jsx` is deliberately written one-element-per-line and dense — preserve that when editing it.

**`Button` takes `variant`, `size` and `to` — never colour or padding classes.** `variant` ∈ `primary` | `secondary`, `size` ∈ `md` | `lg` (both clear the 44px touch target). Passing `to` renders a react-router `<Link>` styled as a button instead of a `<button>`; a **disabled `to` falls back to `<button disabled>`**, because `aria-disabled` on an anchor still leaves it tabbable and still follows the href. Never nest `<Button>` inside `<Link>` — a `<button>` inside an `<a>` is invalid HTML and the nesting is what `to` exists to remove. And never pass `bg-*` / `text-*` / `px-*` / `py-*` to it: those land in the same cascade layer as the component's own utilities, so stylesheet order decides the winner, not class-attribute order. Add a variant or a size instead.

**Charts are hand-rolled in [Charts.jsx](frontend/src/components/Charts.jsx), not a library**, for three reasons that all matter here: colours come from the theme tokens so dark mode and the print palette work with no extra code; the bars survive `window.print()`, where a JS library has already measured a screen-width container before the paper layout re-measures; and **the number is always printed as text beside the bar**, so a chart is decoration over a readable figure rather than the only place a value exists. That last point is the accessibility contract — the track carries `aria-hidden="true"` because the label and value above it already say the same thing.

Two chart rules exist because breaking them produces a *favourable* misreading, which is the worst kind:

- **`BarGroup` gives negative values no bar at all**, and takes its shared maximum over the positive values only. It used to scale on `Math.abs`, so a ₹10,000 loss drew exactly the bar a ₹10,000 profit drew — and in a group of {money in, money out, money left} a long bar reads as "plenty" to anyone not also parsing the minus sign. A shortfall draws an empty track and `.ui-bar-value.is-bad` colours the figure so the empty track cannot read as missing data.
- **A group must share one maximum.** Scaling each bar to its own value makes ₹5,000 and ₹5,00,000 draw identically.
- **The scheme-fit chart plots one bar per `fit_basis`, not one per scheme, and the bar length is how MANY schemes have that basis.** That inversion is forced by the scorer: only two scores are reachable, so per-scheme bars draw a dozen bars of at most two near-identical lengths — and on a category where every match is nationwide, a dozen *identical full-length* bars, which reads as a perfect fit for all twelve. Grouping says the one thing this data honestly can: how many of your matches are made for your state (or for a few states including yours), and how many are for all of India. The labels come from `fitLabel()` in `backendText.js`, the same map the cards use, so the chart and a card cannot describe one scheme two ways. **It grouped on `match_score` and was labelled "90% match" / "100% match" until 23 Sept 2026** — do not bring either back. It returns `[]` below two groups, so it does not render for Delhi, Bihar, or UP agriculture and dairy, where every match is `national`; in a state UNNATI or Vibrant Villages names it draws `region` against `national`.

**Chart data that a page derives lives in [chartData.js](frontend/src/components/chartData.js), not in `Charts.jsx`.** `schemeFitItems(schemes, t)` is there because `react-refresh/only-export-components` fails a component file that also exports a plain function — Fast Refresh cannot tell which export is safe to hot-swap, so it gives up on the whole module. A `.js` sibling was the fix rather than an eslint-disable, because the rule is reporting a real DX regression. Two things about it are load-bearing: **both `/analysis` and `/schemes` import the same helper**, because they carried the same chart under *different gates* and the ungated copy was drawing the exact misreading the gated one existed to prevent; and **it returns `[]` when there is nothing to compare**, so a caller's gate and its data are one expression and cannot disagree. `/schemes`'s old gate was itself unsatisfiable — a `scored.length <= 6` cap on a list that is 0 or 11–16 — so the chart and its eight translated strings were dead code for as long as they existed. A gate written as a separate condition from the data is how that happens.

`UnitChart` (10 coins, first N filled) is the one chart that needs no numeracy at all, which is why the result pages lead with it. It takes `ariaLabel` from the caller so the sentence is translated; the English default is a fallback, not the norm.

**Decorative emoji and glyphs need `aria-hidden="true"`** — either on the glyph's own `<span>` or on a parent that contains nothing else. A screen reader announcing "rocket emoji" or "rightwards arrow" before every button label is noise. Check the parent first: `.ui-feature-icon` wrappers and the `icon=` props on `MiniCard`/`Feature`/`AdvisoryCard` already carry it, so wrapping again is redundant. Numbers that are content (a step number, a scheme's position in a list) stay visible to the reader.

**Guard on the raw value before printing a number, never on `Number.isFinite` alone.** The backend sends `None` for anything it could not compute, which arrives as JSON `null` — and `Number(null)` is `0`, which *passes* `Number.isFinite`. So a naive formatter turns "could not compute" into a confident `0%`, the most favourable possible reading. A `!== undefined` check has the same hole and yields the literal string `"null%"`. Both were live bugs. Use `hasNumber(value)`, which rejects `null`, `undefined` and `''`. **Four** fields go null: `risk_analysis.pressure_ratio_percent` (non-positive surplus), `business_analysis.estimated_roi_percent` (zero investment), `financial_analysis.profit_margin_percent` (zero revenue) and `business_analysis.operating_margin_percent` (zero revenue). A genuine `0` must still render as `0%` — don't collapse real zeros into "Not available".

**This count has been wrong twice, in the same direction each time** — it said "two" until `profit_margin_percent` was added, then "three" until `operating_margin_percent` was. Both times the newly-nulled field was the *twin* of one already on the list, computed by the same "a margin is a share of revenue" reasoning in a different service: `profit_margin_percent` in `financial_service.py` and `operating_margin_percent` in `business_service.py` both divide by `expected_monthly_revenue`, so a fix to one is a fix owed to the other. The `operating_margin_percent` change also needed a **second** edit inside the same function that has nothing to do with rendering: the observation bands compare it against 10 and 30, and **`None < 10` is a `TypeError` in Python 3**, so returning `None` without an `is None` guard first crashes the request rather than printing badly. `advisory_service.py` guards the same way for the same reason. If a fifth field goes null, check every comparison against it before checking every formatter.

**ESLint 10 enforces `preserve-caught-error`.** If you bind a caught error and throw a new one, pass `{ cause: error }` or the lint fails. Bare `catch {}` with no binding is exempt.

**CSS cascade layers — read this before touching `index.css`.** Tailwind v4's `@import "tailwindcss"` emits `@layer theme, base, components, utilities`. **Unlayered author declarations beat all layered ones regardless of specificity.** This cuts both ways and explains four separate things: the default card padding sits inside `@layer components` so a call-site `p-5` or `p-0` still wins; `.ui-feature-card { padding: 22px }` is unlayered so it beats that default; the element resets now sit in `@layer base` so `text-*` utilities win on anchors (defect 6); and the `:focus-visible` outline is deliberately left unlayered so it cannot be removed by `focus:outline-none`. When adding a `.ui-*` rule meant to be overridable by Tailwind, put it in `@layer components`; when adding an element reset, put it in `@layer base`.

**Two competing Tailwind utilities for the same property do not resolve by class-attribute order** — they land in the same layer, and generated-stylesheet order decides. That is why `Button` uses `variant` and `size` props rather than accepting `bg-*` or `px-*` from call sites. If you catch yourself passing a colour or padding class to a component that already sets one, add a variant or a size instead.

**Print styles live in the `@media print` block at the end of `index.css`.** Anything added to `/report` that is a card needs to be covered by the `break-inside: avoid` selector list, or it will split across a page break in the PDF.

**Timing goes through `--motion-fast` / `--motion` / `--motion-ease`, never a literal duration** — and a new transition must name its properties, never `all`. Ease colour by preference; a layout property (`width`, `height`, `padding`, `font-size`, `transform` on a resting state) moves geometry under the fixed sleeps every browser verifier measures at. Run `node tools/verify/motion-audit.mjs` after adding one: it is the only thing in the suite that can see whether a transition runs, and an **undefined** token silently deletes the whole declaration rather than falling back. See the motion-layer section for the full reasoning, including why the `prefers-reduced-motion` guard has to stay in `@layer base`.

**Adding a route, a `<Link>`, or anything that navigates means running `node tools/verify/scroll-audit.mjs`.** It is the only script in the suite that performs an *in-app* navigation — every other one loads each page cold, at offset 0 by definition, so none of them can see a page that opens halfway down. The scroll reset lives in `useOpenAtTop()` in `App.jsx` and it deliberately does nothing when `location.hash` is set; if you add a same-page anchor, that arm is what protects it. See the "Every route opens at the top" section.

**`.ui-field` exists so two controls sharing a grid row start on the same line.** A grid row is as tall as its tallest cell, but each control sits directly under its *own* question — so the moment one question wraps to more lines than its neighbour, that cell's control drops and the pair visibly separates. English already did it on the longest question on `/business`, and every Indic translation is longer, so switching language made it worse rather than better. The rule is `display: flex; flex-direction: column` plus `.ui-field > :first-child { margin-bottom: auto }`, which collects the cell's spare height **under the question** instead of under the control. Two details are load-bearing: the auto margin goes below the *first* child rather than above the last, so the hint and the input keep their own `mt-1` / `mt-2` — putting it on the control would replace its `mt-2` and close the gap on the tallest cell. And it is applied to the `<label>`, not a wrapper. Guarded by `field-align.mjs`; converted at 10 call sites across `BusinessPage`, `LocationPage` and `FinancePage`'s shared `InputField`. Single-column pages (`/profile`, `/login`) do not need it and did not get it.

**The required-field asterisk had two independent causes and the second one is not a markup problem.** The marker was sitting alone on a line of its own beneath a question that had wrapped, and that extra line was itself a cause of the misalignment above. Removing the space before the `<span>` in the JSX was necessary and **not sufficient** — measured, the marker still orphaned at 17 widths with no space anywhere in the markup and with `overflow-wrap` computing to `normal`, so neither whitespace nor the inherited `anywhere` from `.ui-card` was responsible. The real cause is Unicode: every question here ends in a question mark, UAX #14 gives `?` the class **EX** and `*` the class **AL**, and the pair table *permits* a break between them. **No amount of editing the markup removes a break opportunity the line-breaking algorithm derives from the characters.** The fix is `.ui-required::before { content: "\2060" }` — U+2060 WORD JOINER, which rule **LB11** forbids breaking on either side of, applied before the pair table. As a pseudo-element it covers all twelve call sites at once and cannot be forgotten at a new one, it is zero-width so nothing about the rendering changes, and every `.ui-required` span is `aria-hidden`, so the generated character reaches no screen reader. It also survives someone putting the space back. Note that Lightning CSS minifies this to `.ui-required:before{content:"⁠"}` with a *literal* U+2060 — it is present in the built CSS, just not findable by grepping for `::before` or `2060`.

**The brand mark is inline SVG in [BrandMark.jsx](frontend/src/components/BrandMark.jsx), for the same three reasons the charts are hand-rolled** — one asset serves both themes and the print palette (four mode combinations until high contrast was removed), it stays crisp at 38–54px where a gradient PNG blurs, and it prints. It replaced an `अ` in a rounded tile on 8 Sept 2026. Six things about it are load-bearing:

- **Every colour is a `--mark-*` token in `index.css`; never hardcode a hex in the component.** `:root` carries the full colour palette and `[data-theme="dark"]` flips only `--mark-edge` (a deep-plum hairline vanishes against a navy masthead). There was a third block, `[data-contrast="high"]`, collapsing **all** of them to `var(--color-btn)` over `var(--color-bg)`; it is gone, but the trick it turned on is worth remembering — **`var()` inside a custom property resolves at use time on the element**, so that one block served both HC themes with no extra rules.
- **SVG presentation attributes do not accept `var()`; CSS properties do.** Hence `style={{ fill: 'var(--mark-coin-ring)' }}` rather than `fill="var(…)"`, and `style={{ stopColor: … }}` on the gradient stops. `stroke` and `stroke-width` inherit in SVG, so the petal edge is set once on a wrapping `<g>`.
- **The petal hairline is structural, not decoration.** The petals overlap, so where two meet the outline is the only thing separating them. `--mark-edge-w` stays a token even though only one value is now used: it went `2.4` → `3.4` for the removed high-contrast mode, and the reason it had to is the reason it stays adjustable — 2.4 units is about a third of a pixel at 46px, so a colour change alone would not have been enough.
- **`@media print` restates the whole colour palette inside its token-reset block.** Still needed with only two themes: `[data-theme="dark"]` overrides `--mark-edge`, so without the reset what comes out of the printer depends on the theme the laptop was in. The list is exhaustive on purpose — every failure of this block has been a *forgotten* token rather than a mishandled one, which is why `print-audit.mjs` asserts invariance across modes instead of checking a curated few. The extreme case was the high-contrast palette, which resolved `--mark-*` to `#FFE000` and put an invisible yellow logo on white paper.
- **There is no tile behind it, and there must not be one.** The old `अ` sat on a square filled with `--color-btn`, which was `#FFE000` in the then-existing dark high contrast: a magenta-and-gold lotus on a yellow chip. A mark with its own silhouette needs no plate, and without one it sits correctly on the masthead, on a card and on paper with no special case per mode.
- **The three size classes are set from the flower, not from the box.** `viewBox="13 0 94 122"` includes the three falling coins, so the flower is only the top ~75% — a 46px box drew a 34px flower, which read undersized next to the two-line brand block. `.ui-brand-mark` is 54px, `-sm` 38px, `-lg` 88px, and the `max-width: 800px` override is 46px.

`public/favicon.svg` is the **one** copy that hardcodes its hexes, because a favicon is fetched as an image and cannot see the page's custom properties. It also drops the `₹` and thickens the edge to `4`, since at 16–32px the glyph is three pixels of mud and a hairline disappears. Keep its geometry in step with the component.

**Two independent presentation switches on `<html>`, both persisted**, and anything added to `index.css` has to survive both: `data-theme="dark"` (`sih-theme`) and `--ui-scale` (`sih-textsize`, one of 0.94 / 1 / 1.18). It was three until 8 Sept 2026, when `data-contrast="high"` (`sih-contrast`) was removed — see the last entry in the 8 Sept list. The text scale **multiplies** the reader's own browser font size rather than replacing it, so someone already running their browser at 20px keeps that. Sizes that must scale with it need `rem`/`em` or `calc()` against `--ui-scale`, not fixed `px`.

### Phones (7 Sept 2026)

**The target user reads this on a phone, not a laptop**, so narrow-width behaviour is correctness, not polish. Before this work every one of the ten routes scrolled sideways at all three phone widths, and all seven accessibility controls were under the 44px touch minimum. Measured clean now: **40 page loads (10 routes × 360/390/412 plus a 360 stress pass), 0 findings.** Desktop was re-verified unchanged in the same pass — `drive.mjs` 36/36, parity 584 keys (**629 now**), 151 tests (**187 now**).

**The stress viewport is the one that earns its keep.** `360-stress` is 360px *and* dark *and* the 1.18 text scale *and* Hindi, all at once, because `index.css` has to survive every combination of the switches and the narrowest screen with the largest type is where a fixed box overflows again. The three plain widths were clean when it was added; it immediately found four defects the others could not. It carried high contrast as a fourth arm until that mode was removed on 8 Sept 2026 — the remaining combination is still the one that finds things.

There are now **three** breakpoints in `index.css`, and they do different jobs. Don't collapse them:

| Query | Job |
|---|---|
| `max-width: 800px` | pre-existing — collapses the grids and narrows the chrome containers to `min(100% - 24px, 680px)` |
| `pointer: coarse`, `max-width: 640px` | touch-target sizing. **Pointer, not just width**, because a tablet has a thumb at 1024px too; the width arm is there so a narrow desktop window gets the same treatment and so the audit sees it either way |
| `max-width: 640px` | narrow-layout-only fixes: `overflow-wrap: anywhere` on `.ui-page-title` / `.ui-bar-label`, and the nav scroll hint |

Six things are worth knowing before touching this:

- **The whole-page sideways scroll was one missing declaration.** `.ui-utilitybar-inner` already wrapped, but `.ui-utilitybar-tools` inside it was `display: flex` with no `flex-wrap`, so the language select + the `A-/A/A+` trio + three icon buttons formed one unbreakable ~396px row inside a 336px box. That single overflow pushed the document 73px wide on **every route in the app**. It now has `flex-wrap: wrap`.
- ~~**The prototype notice is visible on phones again.**~~ **SUPERSEDED 8 Sept 2026** — the notice is off the page in all viewports now; see the design-direction section for why and what replaced it. The mechanical half of this bullet still holds and is why the `flex-wrap` below matters: the utility bar used to be one unwrappable row, so anything in it that could be dropped got `display: none` below 800px. Now that `.ui-utilitybar-tools` wraps, the tools break across as many rows as they need, so nothing in that strip has to be hidden to fit a phone. (The wordmark shared that strip until 11 Sept 2026 and took a full-width row of its own; with it gone the strip is tools-only and `.ui-utilitybar-inner` is `justify-content: flex-end` — **`space-between` with a single flex child puts it at flex-START**, which would have parked the tools on the left.)
- **`.ui-navbar-inner` keeps its `overflow-x: auto` and hidden scrollbar *on phones only*** — that is a deliberate design decision there, and its links are already ≥44px. What was added is a *hint*: a `::after` fade on `.ui-navbar` below 640px, because the last link was being sliced mid-word ("Your busi") with nothing to say more existed, which reads as broken rather than scrollable. The gradient runs to `var(--color-btn)`, the band's own background, so dark mode needs no extra rule. **Above 640px it now wraps instead — see the next bullet.**
- **The nav wraps on desktop and scrolls on phones, and that split is deliberate.** `.ui-navbar-inner` used to be `overflow-x: auto` at *every* width while the scroll-fade hint existed only below 640px, so on a laptop or a projector a long-script translation truncated the nav in total silence: at 1440px **Tamil overflowed 284px and dropped "Advice" and "Report"; Malayalam overflowed 393px and left a bare label-less icon sliced at the right edge**. A mouse has no easy horizontal-scroll gesture, so those links were unreachable, not merely off-screen. Fix: `flex-wrap: wrap` plus a link-padding trim from `12px 14px` to `12px 11px` (54px back, enough to keep Kannada, Telugu, Marathi and Bengali on one row). Tamil and Malayalam now take **two full rows carrying all nine links**, which reads as deliberate. Phones keep the swipe — `flex-wrap: nowrap; overflow-x: auto` is restored inside the `max-width: 640px` block, because wrapping nine links at 336px stacks five rows deep and buries the page, and a swipe is a gesture a thumb already has. **`mobile-audit.mjs`'s `OVERFLOW` exclusion depends on that ancestor still scrolling below 640px** — if you make the nav wrap on phones too, every nav link starts reporting `OVERFLOW`.
- **`min-width`, not padding, on the breadcrumb link.** Height alone does not make a target: `Home` is ~35px wide, so it stayed a 35×44 box. `min-width: 44px` keeps the text flush with the left edge of the page content below it and does nothing once a longer translation (Hindi `मुख्य पृष्ठ`) already exceeds it. Padding would have shifted the text and misaligned the column.
- **The footer's journey links were deliberately left alone.** They are inline links separated by `·` inside a single `<p>`; a 44px box on each would blow the line height apart, and the nav bar above already offers every journey step at full size. The audit excludes inline links inside `p`/`li` for the same reason — if you "fix" these, you are fighting the tool on purpose.
- **A money figure must never wrap mid-number, and `overflow-wrap: anywhere` will do exactly that.** `.ui-card` and `.ui-card-soft` carry `anywhere` **unconditionally** (index.css:571 and :580), every descendant inherits it, and in a squeezed `.ui-bar-head` flex row that rendered `₹30,000` as `₹30,00` / `0` on **9 of the 40 pages** — a reader parses a different number, and it happens to be a smaller, more reassuring one. The fix is two halves and both are load-bearing: `.ui-bar-label { min-width: 0 }` so the *label* absorbs the squeeze (a flex item will not shrink past min-content without it), and `.ui-bar-value { flex-shrink: 0; overflow-wrap: normal; word-break: keep-all }` so the *figure* neither shrinks nor breaks. Both are unconditional, because the ingredients are width-independent. Anything new that prints a figure into a narrow flex row needs the same opt-out, and `mobile-audit.mjs` guards it as `SPLIT-FIGURE`.

Five back links on `/login`, `/profile`, `/business`, `/location`, `/finance` were 20px tall; they now carry `inline-flex min-h-11 items-center`, which is the pattern the four result pages already used. Then **all eight** (those five plus `/analysis`, `/schemes`, `/advisory`) gained `min-w-11`, because Hindi `← होम` measures only 42px wide — the existing four were never as safe as they looked. `ReportPage`'s two `inline-flex min-h-11` hits are `<div>`s, not links, and are correctly left alone. **These plus the chart rules above are the only changes here visible on desktop** — those back-link rows are 44px tall now instead of 20px.

Watch `--ui-scale` when adding a font size here: `0.75rem` is 12px at scale 1 but **11.28px at the 0.94 scale**, which is a `TINY` finding waiting to happen. `.ui-brand-sub` moved from `0.74rem` to `0.82rem` for exactly this reason.

**That lift is now the base rule, and the phone-only override is deleted — which is a correction to what this section used to say, not a detail.** `0.82rem` first landed *inside* the `max-width: 640px` block, so it read as a phone fix and it was documented here as one. It never was: `html` is `calc(100% * var(--ui-scale))`, so `0.74rem` is 11.84px at scale 1 and 11.13px at 0.94 — **under the 12px floor at every width**, desktop included. The override merely hid the defect from the one tool that measures type size, because **`mobile-audit.mjs`'s `TINY` check runs at phone widths only**, i.e. at exactly the widths where the value had already been fixed. Two transferable lessons: a font size expressed in `rem` is width-independent, so "fix it in the phone block" is almost always the wrong shape; and a check scoped to one viewport will certify a defect clean in every other one. Nothing in the suite measures desktop type size — the four remaining `0.78rem` strings (index.css :343, :453, :744, :1630) fall to 11.73px at the 0.94 scale and are accepted as-is, on the record rather than by omission.

Still unverified on phones: landscape orientation, real touch scrolling on physical hardware, and the on-screen keyboard covering a focused input.

**UI copy is for low-literacy users, and that is a product requirement, not a style preference.** Plain language over jargon ("Money needed", "Money left each month", not "funding gap" / "net surplus"). Advanced detail hides inside `<details className="ui-disclosure">`. Every page carries a back link and a "Step N of 4" marker. Don't "improve" labels into financial terminology — and don't add the terminology in translation either, where it is harder to notice.

**Two labels on `/analysis` and `/finance` describe different figures and must not be given the same words.** `money.left` is the pre-EMI monthly surplus (`revenue − expenses`); `money.leftAfterEmi` is after the loan payment. `monthly_profit` is pre-EMI **on purpose** — `risk_service.py` divides the EMI *by* it to get repayment pressure, so the EMI must not already be subtracted. Labelling both "money left each month" was a live bug.

## Tests

```bash
cd backend && ../.venv/Scripts/python.exe -m pytest tests -q     # 187 passed in ~1s
```

Backend only — there are no frontend tests. `test_frontend_contract.py` and `test_mvp_api_contract.py` pin the response shape by subscripting every key, so **removing or renaming a response key raises `KeyError` and fails them** — that is intended, and it is the fastest way to check whether a contract change is safe. Note the corollary: they assert only that the documented keys are *present*, so **adding** keys passes silently. Run the suite after any service or schema edit.

That corollary is exactly why defect 4 survived so long: `test_frontend_contract_financial_section` asserted precisely the four keys the backend happened to return, encoding the *current* behaviour rather than what the UI needed. It now also asserts the four added keys plus `funding_gap == 0` for the surplus case, and `test_frontend_contract_funding_gap_when_capital_falls_short` pins the shortfall case against `/report`'s own arithmetic.

Some tests pin user-visible **wording**, not behaviour, and are meant to be edited alongside a copy change — `test_scheme_service.py` asserts substrings of `match_reasons`. Those strings now appear on `/analysis` (defect 7), so they are UI copy and bound by the plain-language rule. Two market tests were also rewritten when the district fallback landed: `test_market_context_falls_back_to_the_same_state` replaced one that asserted `[]` for UP/Kanpur.

**The 8 Sept audit added a test class this suite did not have: one that asserts a branch is *reachable*.** An ordinary unit test calls a function with the input for a branch and checks the output, so it passes whether or not any real request can produce that input — which is exactly how `nxt.reviewExpenses` and `mvp_summary.status == "review"` stayed dead. `test_priority_advice_is_reachable_through_the_real_pipeline` instead sweeps a grid of realistic inputs **through `run_unified_analysis`** and asserts every code and every status value appears at least once; that is what caught the two unreachable ones, over 480 cases. The same shape does the same job elsewhere: `test_the_seven_levels_stay_reachable_for_every_kind_of_place` (no tier becomes dead data for rural, semi-urban or urban), `test_every_scheme_in_the_file_is_reachable_from_a_category_button` (no scheme is in the file but off every path), `test_every_band_edge_agrees_with_its_printed_figure`, and `test_no_scheme_is_offered_for_work_its_own_rules_exclude` — which reads the eligibility prose and is the only test that can catch a dataset self-contradiction. **When adding a branch, add the test that proves an actual request can reach it**, not just the one that proves it works when called.

**The 9 Sept optimization pass added a second class this suite did not have: one that asserts a *cache* cannot be poisoned.** `load_json` is now `lru_cache`d, so the object it returns is shared across every request in the process — and a service that mutated it would corrupt later requests **silently**, with the file on disk still correct and a restart making the symptom vanish. There is nothing an ordinary unit test can see there, because a single call always looks right. `test_a_response_cannot_poison_the_cached_scheme_dataset` and `test_a_response_cannot_poison_the_cached_market_rows` run a real request, mutate what came back the way a careless caller would, then re-run and assert the second result is unaffected — one test per data file. If you add a service that reads `load_json`, add the third.

`httpx2` in `requirements.txt` is correct and intentional, not a typo for `httpx` — it is the httpx 2.x line published by the pydantic org, and Starlette 1.6 uses it directly. `import httpx` fails in this venv while `TestClient` works.
